# 架构总览 Skill（arch-overview）— 功能需求文档

> 本文档只描述这个 skill「做什么功能」，不涉及交互/UI/技术实现（多语言依赖解析方案、AST/目录启发算法、评分聚合公式等一律记入「未决问题」留给后续技术设计）。
> 范围档位：**标准版**（MVP 闭环：范围界定 + 3 视角架构图 + 4 维正向总评含业界做法对照 + 双轨产物 + 门禁）。
> 日期：2026-07-10。

---

## 1. 一句话目标

一个 skill，针对**一个模块或一个 app**（每次由用户指定范围），先**画出其架构**（分层/模块依赖、C4 Container/Component、运行时/数据流三个视角的 Mermaid 图），再从**正向设计视角**用 4 维 rubric 评估其**整体优秀度**（每个维度对照业界成熟做法），产出一份「**看懂这个架构 + 判断其设计如何**」的架构总览报告（`overview.json` 机器契约源 + `overview.md` 人读渲染，过门禁），帮**接手者/评审者**快速建立架构认知与设计判断。

只回答两个问题：**这个模块/app 架构长什么样**（图）+ **它的整体设计好不好**（正向总评，带业界对照）。**不回答**「坏味道逐条在哪」「要不要重构」「该重构成什么样」——那是 `arch-quality-eval` 的定位。

```
一个模块或 app 的代码路径 ──► [arch-overview] ──► 架构总览报告（overview.json + overview.md，过门禁）
                                  │
                                  ├─ 3 视角 Mermaid 架构图（带证据回链）
                                  └─ 4 维正向总评（现状评价 + 业界做法对照 + 分维度评分 + 整体档位 + 亮点/风险）
```

## 2. 目标用户

- **主要用户**：**刚接手 / 要评审一个 app 或模块的人**——开发者 / 技术负责人 / 架构师 / 新人，手上有个需要先**看懂**、并判断**整体设计如何**的模块或 app，要在动手改之前建立架构认知与设计判断。
- **次要用户**：
  - 要**产出架构文档底稿**的人（图 + 总评可作为文档起点）。
  - 做**技术选型 / 方案对比**的人（总评 + 业界对照作为对比维度之一）。
- **不是**目标用户：
  - 想找**具体架构坏味道 / 判断要不要重构**的人（用 `arch-quality-eval`，本 skill 不深挖不分级）。
  - 想画**部署 / 运维拓扑图**的人（本 skill 不画部署视图）。
  - 想要**完整重构方案 / 迁移步骤**的人（本 skill 只总评、指亮点与风险，不给方案）。
  - 想要**联网核实业界做法的权威引用**的人（本 skill 业界做法为内置经验 + 延伸阅读方向，不联网）。

## 3. 核心场景

- **接手读懂**：新人/接手者拿到一个模块或 app → skill 画 3 视角图让其快速看懂结构 + 给整体设计总评，建立认知。
- **架构评审**：评审一个 app/模块设计 → 用图 + 4 维 rubric 总评 + 业界做法对照，形成可沟通的评审意见（分维度档位 + 整体档位 + 亮点/风险）。
- **新人 onboarding**：团队新人通过图 + 总评快速建立架构心智模型。
- **架构文档底稿**：用产出的图 + 评估作为正式架构文档的起点（图与评估均带证据，可二次加工）。

## 4. 功能清单

### 模块 A：输入与边界界定

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 范围档位指定 | 接受用户指定本次分析是**模块级**还是 **app/服务级**，并接受对应的根路径（可跨多目录） | 报告明确记录用户声明的范围档位（模块/app）+ 覆盖的目录/包/服务集合；两种档位均能处理 |
| P0 | 多语言技术栈识别 | 识别范围内的主要语言（Python / Go / JS / TS / 前端 / JVM / C++ 等）及其包/目录/模块组织结构 | 正确识别范围内占比显著的语言；对每种语言**标注其结构/依赖分析的可获精度**（哪些语言精度高、哪些靠目录/import 启发） |
| P0 | 覆盖范围枚举 | 枚举本次分析覆盖的文件/目录/包/外部依赖集合 | 报告列出覆盖集合；跨多目录的范围边界清晰，无关键包遗漏也无明显无关代码混入 |
| P1 | 两段式范围确认（HARD-GATE） | 把「范围档位 + 根路径 + 覆盖集合 + 识别到的技术栈 + 一句话架构职责推断」呈现给用户确认 | **范围未经用户确认前，不进入画图或评估、不产出任何内容**；确认动作可追溯 |

### 模块 B：架构图生成（三个视角，Mermaid）

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 分层/模块依赖图 | 画代码结构视角：模块/包/层之间的依赖关系，体现分层与依赖方向 | Mermaid 产出；节点/边均回链代码证据（包/目录/文件/依赖边）；依赖方向在图中可见 |
| P0 | C4 Container/Component 图 | 画系统组成视角：服务、存储、外部依赖、内部组件的组成与关系（按范围档位选 Container 或 Component 层级） | Mermaid 产出；每个容器/组件标注其类型与职责；与外部依赖的边界清晰 |
| P0 | 运行时/数据流图 | 画运行时视角：一次典型请求/操作在架构中的流转路径、调用时序、数据流向 | Mermaid 产出；流转路径的每一步回链到对应的代码入口/调用点（证据可定位） |
| P0 | 视角适用性显式声明 | 当某个视角在当前范围**信息不足或确不适用**时（如纯库模块无运行时入口），不得静默省略 | 显式标注「本视角不适用/信息不足」并说明原因，而非不出图；默认 3 视角全画 |
| P0 | 图节点证据回链 | 图中每个节点/边/流转步都可追溯到代码 | 节点挂证据（包/文件/类/依赖边）；无法定位的节点必须标 `⚠ 未确认`，**禁止编造节点或边** |

### 模块 C：架构总评（正向 rubric + 业界做法对照）

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 四维正向评估 | 对 4 个维度逐维度评估现状：① 分层 & 依赖方向 ② 职责内聚 & 边界 ③ 可扩展性 & 可变性 ④ 可读性 & 命名表意 | 4 维**逐维度必须有结论**（全覆盖，不漏维度）；每维度结论挂证据（回链代码事实） |
| P0 | 业界成熟做法对照 | 每个维度在评现状的同时，给出**该维度的业界成熟做法**作为对照标杆，并指出现状与标杆的差距方向 | 每条业界做法含：① 一句话该做法是什么 ② 适用场景/前提 ③ 现状与标杆的差距点；**每条声明 provenance（内置经验）+ 核对状态（未核对原文）** |
| P1 | 业界做法延伸阅读 | 为每条业界做法附**可去查的方向**（关键词 / 经典资料名 / 模式名），供用户自行核实 | 每条业界做法至少附一个可检索的延伸方向；声明为「通用经验·未核对」，**不联网** |
| P0 | 分维度评分 | 每个维度给一个档位：**优 / 良 / 中 / 差**，每档带**客观判定依据**（现状事实 + 与业界做法的差距），非主观打分 | 每维度档位可用客观依据说清（现状事实 + 差距），不是「感觉像优」；档位判定可解释、可复现 |
| P0 | 整体档位 | 汇总 4 维给出**整体优秀度档位**（优 / 良 / 中 / 差） | 整体档位与各维度档位**可解释地一致**（有汇总依据，非简单平均或随意给）；汇总规则在报告「评估方法」中说明 |
| P0 | 亮点 & 风险点 | 列出**亮点**（设计得当、值得保持的选择）与**风险点**（从正向设计视角看、未来可能演进成问题的选择） | 每条亮点/风险挂证据 + 指向所属维度；**风险点是总览级、前瞻性、描述性的**，不分级、不给重构方案、不下 go/no-go |

> **与 `arch-quality-eval` 的边界（关键）**：本模块的「风险点」是**总览级别、前瞻性、描述性**的（"这个选择在未来 X 场景下可能……"）；`arch-quality-eval` 的「坏味道」是**具体、分级（critical/major/minor）、带 go/no-go 重构决策信号**的。两者不重叠：本 skill **不做坏味道逐条分级、不下 go/no-go、不给重构优先级**。

### 模块 D：产物生成（双轨 + 门禁）

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 机器契约源 `overview.json` | 把图的结构化定义（节点/边/视角）+ 评估 findings（维度/档位/业界对照/亮点/风险/证据）结构化为稳定契约源 | 字段稳定、带稳定 id；图节点与评估 finding 均挂证据；含 provenance/核对状态字段（业界做法条目） |
| P0 | 人读渲染 `overview.md` | 把 `overview.json` 渲染成人读报告：3 视角 Mermaid 图 + 4 维总评 + 业界对照 + 整体档位 + 亮点/风险 + 评估方法与已知缺口 | 含 frontmatter（范围/技术栈/整体档位/日期）；mermaid 图可渲染；与 `overview.json` 一致 |
| P0 | 门禁校验 | 交付前跑校验脚本：json schema/枚举/证据、md 渲染完整性、json↔md 一致性、业界做法 provenance 声明 | 4 类校验全过才交付；任一不过则回到对应步骤修订；**未过门禁不交付** |
| P1 | 已知缺口登记 | 把分析过程中的精度受限、信息不足、未能确认之处记入「已知缺口」 | 缺口显式列出，不混入正文当事实；多语言精度差异在缺口中体现 |

## 5. 明确不做（Out of scope）

- **不做架构坏味道逐条诊断 / 分级**：不输出 critical/major/minor 坏味道清单、不挂「违反了哪条原理」逐条诊断（那是 `arch-quality-eval` 的定位；本 skill 只给总览级亮点/风险）。
- **不下 go/no-go 重构决策信号**：本 skill 是理解 + 总评，不是重构前诊断，不给"要不要重构"的门禁判定。
- **不给完整重构方案 / 迁移步骤 / 目标架构**：只指亮点与风险方向，不画目标架构、不写迁移（那是重构阶段的事）。
- **不画部署 / 运维拓扑视图**：不做部署图、不做基础设施/云资源拓扑。
- **不联网核实业界做法**：业界做法为 LLM 内置经验 + 延伸阅读方向，声明未核对，不主动联网检索权威引用。
- **不做模块化度量**（LCOM/扇出/不稳定性/距主序列等纯数值）：数值不当判定依据，只当线索。
- **不做独立 SOLID 逐条合规检查**：设计原理通过维度评价 + 业界对照间接体现，不单独逐条对照 SRP/OCP/LSP/ISP/DIP。
- **不自动解析项目架构文档 / 复用代码内规约**（ArchUnit / dependency-cruiser 等）：本期不读取项目已有架构断言。
- **不做全 repo 批量巡检**：单次分析一个用户指定范围（模块或 app），不做批量盘点出全景矩阵。
- **不做评估结果历史对比 / 趋势**：单次总览即可。
- **不主动修改代码**：只读分析 + 产出报告，不改任何源码。
- **CI PR 自动卡关 / Code Review 场景**：定位理解 + 总览，不做 CI 自动门禁。

## 6. 非功能约束

- **语言/技术栈**：**多语言通用**（Python / Go / JS / TS / 前端 / JVM / C++ 等）。因语言差异，结构/依赖分析精度**因语言而异**：有规范包/模块系统的语言（如 JVM、Go、TS）精度较高；靠目录约定/import 启发的语言（如 Python、C++）精度受限。结论须按语言精度保守，并在「已知缺口」中体现。
- **范围粒度**：模块级或 app/服务级（跨多目录，范围可能偏大）——存在 **token 压力与噪音淹没关键结构**的风险，skill 必须有聚焦策略（见未决问题）。
- **图格式**：**Mermaid 为主**，内嵌 Markdown（终端/GitHub/CI 可渲染、可 diff、支持 C4/流程图/时序图）。本期不产出 PlantUML/DOT 或位图导出。
- **业界做法来源**：LLM 内置经验，**不联网**；每条声明 provenance（内置经验）+ 核对状态（未核对原文）+ 延伸阅读方向。可信度透明但可能不精确/过时，须让用户知情。
- **证据纪律**：图中节点/边、评估每条结论均回链代码（包/文件/依赖边），找不到的标 `⚠ 未确认` + 登记缺口，**禁止编造证据**。

## 7. 未决问题

- **多语言依赖/结构分析方案**（语言无关的目录/import 启发？各语言 LSP？混合策略？精度如何按语言标注？）：属技术方案，超出需求澄清范围，留后续技术设计。影响：各语言上图精度与评估可信度。
- **3 视角是否总全画的判定标准**（哪些范围确无运行时入口？C4 该取 Container 还是 Component 的判据？）：需求层已给方向（默认全画、不适用则显式声明），具体判据在 skill 设计时细化。
- **分维度评分（优/良/中/差）的客观阈值与整体档位汇总规则**（整体档位如何由 4 维汇总、是否带权重、边界情形如何定）：在 skill 设计时定（需可解释、可复现，非主观）。
- **app 级大范围下的 token 聚焦 / 噪音控制策略**（热点优先？分层抽样？按服务/模块聚合而非按文件？）：技术方案，留后续。影响：app 级总览是否可用、token 成本。
- **业界做法「延伸阅读方向」的具体形式**（关键词 / 经典资料名 / 模式名 / 可检索描述？是否统一格式？）：需求层已给方向（可检索方向、不联网、标未核对），具体形式在 skill 设计时定。
- **多语言场景下「分层」「模块边界」的统一抽象**（不同语言的模块单元不同：Java 的 package、Go 的 module、前端的组件/目录……如何统一成图节点？）：技术方案，留后续。影响：跨语言 app 上图的一致性。
