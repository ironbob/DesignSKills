# ui-layout-qa Skill 功能需求

## 1. 一句话目标

为主动调用该 skill 的开发者，在 Web、桌面端或移动端 UI 开发与维护场景中，基于代码和/或截图准确发现布局质量问题，在受控范围内修复可修复问题，并以可复核的验证结果减少文字堆叠、布局错位和状态布局失效。

## 2. 背景与成功标准

- 当前问题：未使用专门 UI 设计 skill 时，AI 生成或修改的界面容易出现长文字堆叠、溢出、对齐不一致、内容密度失控、窄窗口失效，以及空、加载、错误状态布局不完整等问题。现有 `ui-design-app` 聚焦风格选择与迁移，不能作为所有 UI 任务的通用布局质量门。
- 成功标准：
  - 开发者可以选择增量或全量模式完成“分析 → 确认适用范围 → 修复（如适用）→ 验证 → 报告”的闭环。
  - 增量修复完成后，目标问题消失，直接关联区域无明显回归，并验证长文本、窄窗口和典型异常状态。
  - 全量模式未经分组确认不得修改对应问题；获确认的分组可分别修复和验证。
  - 全量模式只有在页面清单中不存在待审计或被阻塞的必需检查项时，才能声明页面覆盖完成；每页的验证或未验证状态必须可追溯。
  - 任何诊断或修复前，skill 必须输出文本扫描示意图并获得用户对当前版本的明确确认；该图必须展示其对页面或目标区域结构的理解及未知项。
  - 所有“已修复”或“验证通过”结论都有代码、实际运行结果或现有检查结果作为证据；无法验证时必须明确标记。
- 产品阶段：新建 skill 的首版需求。
- 建议模式：Full——同时涉及两种工作模式、代码与截图输入、直接修复权限、跨平台范围和分级确认，需要系统澄清范围、规则、异常与验收。
- 用户最终选择：Full；用户于 2026-08-21 确认采用标准版 v1 范围。

## 3. 用户与角色

| 角色 | 关键特征 / 目标 | 可以做 | 明确不能做 |
|---|---|---|---|
| 开发者 | 正在创建、修改或维护 UI，希望主动检查并改善布局质量 | 选择模式；提供代码、截图或两者；限定分析范围；确认全量修复分组；查看结果与证据 | 未确认全量修复分组时，不视为授权修改该组问题 |
| ui-layout-qa skill | 按开发者指定的模式分析、修复和验证布局问题 | 在增量模式修复目标及直接关联问题；在全量模式审计并修复已确认分组；记录未处理问题 | 不得擅自修改增量范围外的历史问题；不得把未验证结果声明为通过 |

- **不是**目标用户：只希望选择视觉风格、迁移品牌风格或进行完整无障碍专项审计的用户。

## 4. 核心场景

- 场景 1：开发者完成一次 UI 生成或局部修改后，主动使用增量模式检查目标区域；skill 分析代码和可用截图，直接修复目标及直接关联问题，验证长文本、窄窗口和典型异常状态，并报告结果。
- 场景 2：开发者希望治理已有应用的布局质量，主动使用全量模式指定应用或范围；skill 形成按严重程度或区域组织的问题分组，逐组取得确认后修复和验证。
- 场景 3：开发者只提供代码；skill 从代码表达的预期行为出发识别布局、信息层级、内容密度和状态覆盖问题，并在所选模式允许的范围内继续处理。
- 场景 4：开发者只提供截图；skill 只列出截图中可直接观察和证实的问题，不推断代码原因、不提供修改建议，也不声明问题已修复。
- 场景 5：开发者同时提供代码与截图，但两者不一致；skill 以代码表达的预期行为作为判断基准，把截图作为实际呈现证据，明确记录两者差异。

## 5. 业务对象与术语

| 术语 / 对象 | 业务定义 | 与其他对象的关系 |
|---|---|---|
| 分析目标 | 开发者本次要求检查的 UI 区域、功能或应用范围 | 决定增量范围或全量范围 |
| 直接关联区域 | 与分析目标共享布局关系，且目标改动可能直接影响的父级、子级或相邻区域 | 可纳入增量分析和修复 |
| 布局问题 | 可归因于文字呈现、对齐、间距、尺寸、区域关系或响应式行为的质量缺陷 | 属于问题记录的一类 |
| 内容呈现问题 | 信息层级、内容密度或空、加载、错误等典型状态的呈现缺陷 | 属于问题记录的一类 |
| 问题记录 | 对一个问题的范围、证据、影响、状态和处理结果的描述 | 可被归入一个修复分组 |
| 修复分组 | 全量模式中按严重程度或区域组织、供开发者确认的一组问题 | 获确认后才能进入修复 |
| 证据 | 支撑问题判断或验证结果的代码、截图、实际运行结果或已有检查结果 | 决定结论是否可声明为已验证 |
| 未验证 | 当前证据不足以客观确认问题原因、修复结果或回归状态 | 必须在结果中显式呈现 |

## 6. 业务规则与状态

### 6.1 关键规则

- R1：所有决策严格遵循“功能准确可用性高 > context 节省 > 速度 > token 节省”。低优先级目标不得损害高优先级目标。
- R2：分析应从目标区域和最小必要上下文开始；当证据不足以保证判断准确或修复可用时，必须扩大分析范围，不得为了节省 context、时间或 token 维持低置信度结论。
- R3：代码表达预期行为，截图表达实际呈现。两者冲突时，以代码作为预期基准，并记录截图与预期之间的差异。
- R4：只有截图而没有代码时，只报告截图中可观察、可证实的问题；不得推断代码原因、提供修改建议或执行修复。
- R5：增量模式只分析和修复目标及其直接关联区域；发现无直接关系的既有问题时不修改，只做简短记录。
- R6：全量模式必须先形成问题分组；每个分组获得开发者确认后才可修复。未确认分组保持未处理状态。
- R7：运行环境和现有检查可用时，允许直接运行以验证真实结果；高风险修复应优先进行实际验证。
- R8：没有足够证据时，问题原因、修复结果或回归状态必须标记为未验证，不得默认通过。
- R9：检查范围仅包括布局、信息层级、内容密度和典型状态呈现；视觉风格与完整无障碍审计不自动纳入。
- R10：同一问题已被处理且相关输入未变化时，不重复产生互相矛盾的处理结论；新证据出现时可以更新结论并说明变化。
- R11：诊断前必须建立扫描文本图确认门。每个扫描目标有唯一的文本图、来源锚点、未知项和版本号；用户明确确认当前版本后才能继续。用户修正后必须递增版本并重新确认。

### 6.2 生命周期 / 状态

| 对象 | 当前状态 | 触发事件 | 下一状态 | 谁可触发 | 不允许时的业务结果 |
|---|---|---|---|---|---|
| QA 任务 | 已发起 | 输入与分析范围足以开始 | 分析中 | 开发者 / skill | 输入不足时说明缺口，不伪造结论 |
| QA 任务 | 分析中 | 增量问题已确定 | 修复中 | skill | 超出直接关联范围的问题只记录 |
| 修复分组 | 待确认 | 开发者确认该分组 | 可修复 | 开发者 | 未确认时保持待确认，不修改代码 |
| 修复分组 | 可修复 | 开始处理确认范围 | 修复中 | skill | 发现范围需扩大时停止该扩大部分并重新说明范围 |
| 问题记录 | 已发现 | 产生足够验证证据 | 已验证修复 | skill | 证据不足时进入未验证，不得标记通过 |
| 问题记录 | 已发现 / 已处理 | 无法运行、环境缺失或结果不确定 | 未验证 | skill | 报告限制和剩余风险 |
| QA 任务 | 修复中 | 当前授权范围处理完毕 | 已完成或部分完成 | skill | 未确认分组或未验证问题须保留在结果中 |

## 7. 功能清单

### 模块：输入与基准识别

| 优先级 | 功能 | 业务行为 | 验收标准 |
|---|---|---|---|
| P0 | 代码输入分析 | 开发者提供代码或工程范围时，skill 识别预期 UI 行为及与目标直接相关的布局关系 | 能指出分析目标及直接关联范围；问题结论可追溯到具体代码证据；证据不足时扩大范围或标记未验证 |
| P0 | 截图输入分析 | 开发者只提供截图时，skill 识别截图中直接可见的布局和内容呈现问题 | 结果只包含截图可观察问题；不推断代码原因；不输出修改建议或已修复结论 |
| P0 | 代码与截图联合分析 | 两种输入同时存在时，skill 用代码定义预期，以截图记录实际呈现 | 两者一致时形成相互支持的证据；两者冲突时明确列出差异；不以截图覆盖代码表达的预期 |
| P0 | 跨平台适用 | skill 可处理 Web、桌面端和移动端 UI 工程 | 面对三类工程时均能识别目标与适用检查项；当前证据或能力不足时明确说明限制，不套用不适用结论 |
| P0 | 文本扫描图确认门 | 在诊断或修复前，skill 为每个扫描目标输出带来源锚点和未知项的文本布局示意图 | 每个目标与一张当前文本图一一对应；用户可肉眼检查结构理解；未获明确用户确认不得继续诊断、修复或声称已扫描 |

### 模块：布局与内容检查

| 优先级 | 功能 | 业务行为 | 验收标准 |
|---|---|---|---|
| P0 | 文字呈现检查 | 检查长文字堆叠、截断、换行、溢出及其对相邻内容的影响 | 至少覆盖最长现实文本或等价边界条件；指出受影响区域；修复后不出现非预期遮挡或横向溢出 |
| P0 | 对齐与空间检查 | 检查相关元素的对齐、间距、尺寸和区域关系是否一致且可用 | 可区分目标问题与无关风格偏好；修复后同组元素对齐关系一致；直接关联区域无明显错位回归 |
| P0 | 响应式检查 | 检查目标在窄窗口或小屏条件下是否保持可用布局 | 至少验证一个与目标平台相符的窄窗口或小屏条件；关键内容和操作不因布局失效而不可用 |
| P0 | 典型状态检查 | 检查默认、空、加载和错误等与目标相关的典型状态呈现 | 对实际存在且与目标相关的状态逐项给出已验证、不适用或未验证结论；不得因缺少数据而默认通过 |
| P1 | 信息层级与内容密度检查 | 识别信息主次不清、连续长文堆积或单位区域内容过载 | 每个结论说明其对理解或操作的具体影响；不把个人视觉偏好当作问题；修复不删除必要信息或改变功能关系 |

### 模块：增量模式

| 优先级 | 功能 | 业务行为 | 验收标准 |
|---|---|---|---|
| P0 | 增量范围识别 | skill 围绕本次目标识别直接关联区域，并排除无关历史区域 | 报告明确目标和直接关联范围；无关问题不进入修复；范围不足影响准确性时可说明理由后扩大分析上下文 |
| P0 | 增量直接修复 | skill 对已确认属于目标或直接关联范围的问题直接修复 | 不要求额外逐项确认；不修改无关历史问题；修复保持原有功能与必要信息关系 |
| P0 | 增量验证 | 修复后验证目标、直接关联区域、长文本、窄窗口和典型异常状态 | 目标问题消失；关联区域无明显回归；每个要求都有通过、不适用或未验证结果及依据 |
| P1 | 无关问题记录 | 发现增量范围外的既有问题时，skill 以简短方式记录但不处理 | 记录足以让开发者识别问题区域；不展开无关分析；不产生对应代码修改 |

### 模块：全量模式

| 优先级 | 功能 | 业务行为 | 验收标准 |
|---|---|---|---|
| P0 | 全量范围审计 | skill 对开发者指定的应用或范围检查布局与内容呈现问题 | 审计范围明确；问题覆盖适用检查类别；未检查区域或无法验证项明确列出 |
| P0 | 页面发现与覆盖台账 | 全量模式先发现可达、条件可达和被阻塞的页面，并登记每页默认、长文本、窄布局和关键状态的检查结果 | 每个发现页面都有唯一条目及入口证据；必需检查均有已验证、已审计未验证、不适用、被阻塞或待审计状态；不允许静默遗漏 |
| P0 | 页面覆盖完成门 | skill 在全量报告前校验页面台账 | 存在待审计或被阻塞的必需项时不得宣称页面覆盖完成；只有全部页面覆盖状态闭合时才可声明覆盖完成 |
| P0 | 问题分组 | skill 按严重程度或区域组织问题，并说明影响和证据 | 每个问题只归入一个主要分组；分组边界足以单独授权；未确认分组不进入修复 |
| P0 | 分组授权修复 | 开发者确认一个或多个分组后，skill 只修复获确认范围 | 可一次确认单组或多组；未确认问题保持不变；修复中发现新增范围时不得自动扩大授权 |
| P0 | 分组验证 | 每个获确认分组修复后单独验证并报告 | 每组具有独立处理结果；失败或未验证不会被合并成整体通过；剩余分组状态清楚 |

### 模块：证据、验证与结果

| 优先级 | 功能 | 业务行为 | 验收标准 |
|---|---|---|---|
| P0 | 实际运行验证 | 现有条件支持时，skill 可运行应用或已有检查；高风险修复优先验证 | 有可用验证条件时不无故跳过高风险验证；运行失败时报告原因；不把“已修改”当作“已验证” |
| P0 | 证据与置信度 | skill 区分代码证据、截图证据、运行/检查证据和未验证结论 | 每个已修复问题至少关联一种验证证据；证据不足的结论明确标为未验证；不使用无依据的确定性表述 |
| P1 | 最终结果摘要 | skill 汇总范围、已修复问题、验证结果、未处理问题与限制 | 开发者可从摘要判断本次改了什么、哪些已验证、哪些未处理；增量模式包含无关问题简记；全量模式包含各分组状态 |
| P1 | 按需扩大上下文 | 当局部证据不足时，skill 为保证准确性扩大到必要关联范围 | 扩大范围有明确原因；不因 context 节省阻止必要分析；问题解决后不继续无目的扩大范围 |
| P1 | 共享结构复用与风险排序 | 全量模式先检查共享壳层和组件，再按页面特有区域及风险顺序完成覆盖 | 同一共享结构不在每页重复分析；关键任务、文字密集、窄布局高风险和近期改动页面优先；低风险页面仍纳入覆盖台账 |

## 8. 关键异常与失败结果

| 场景 | 异常 / 边界条件 | 期望业务结果 |
|---|---|---|
| 代码分析 | 目标入口或关联代码不足 | 说明缺失内容；在可访问范围内按需扩大；仍不足则标记未验证 |
| 截图分析 | 截图模糊、裁切或缺少必要状态 | 只报告可观察问题，并列出无法判断的范围；不猜测隐藏内容 |
| 联合分析 | 截图表现与代码预期冲突 | 以代码定义预期，记录实际偏差；不得隐去冲突或把截图视为预期来源 |
| 增量修复 | 问题根因超出直接关联范围 | 停止超范围修改；说明需要扩大的范围和影响；无关区域保持不变 |
| 增量检查 | 发现无关但严重的既有问题 | 简短记录其区域和影响，不直接修复 |
| 全量修复 | 分组未获确认 | 保持待确认状态，不进行对应修改 |
| 扫描理解 | 文本图尚未获确认或用户指出理解错误 | 保持诊断和修复阻断；修订对应图、递增版本并等待重新确认 |
| 全量修复 | 修复过程中发现新增问题 | 将新增问题加入适当分组或作为新增待确认项，不自动扩大修复授权 |
| 运行验证 | 应用无法启动、检查失败或环境不可用 | 保留修改事实与静态证据，但验证状态标记为未验证，并报告限制 |
| 回归验证 | 目标问题消失但关联区域出现明显回归 | 不得声明完成；继续在授权范围内修复，或报告部分完成和剩余问题 |
| 优先级冲突 | context、时间或 token 节省会降低判断准确性 | 优先保证功能准确与可用性，允许增加必要分析成本 |
| 平台差异 | 某项检查不适用于当前平台或界面类型 | 标记为不适用并说明原因，不强行套用其他平台规则 |

## 9. 非功能与领域约束

| 类别 | 约束 / 要求 | 状态 | 依据 / 风险 |
|---|---|---|---|
| 准确性与可用性 | 最高优先级；不得因节省 context、速度或 token 牺牲问题判断、功能保持和验证可信度 | 已确认 | 错误修复或功能回归会直接破坏 skill 的核心价值 |
| context 使用 | 从目标与最小必要范围开始，证据不足时按需扩展 | 已确认 | 过度读取浪费上下文，过少读取会造成误判 |
| 速度 | 在准确可用和必要 context 得到满足后，优先减少等待与重复工作 | 已确认 | 速度不能成为跳过高风险验证的理由 |
| token 使用 | 在前三项得到满足后减少冗余分析和报告 | 已确认 | 过度压缩可能丢失证据和未验证项 |
| 安全与变更边界 | 增量模式不得修改无关历史问题；全量模式不得修改未确认分组 | 已确认 | 防止意外扩大变更范围 |
| 可追溯性 | 已修复与已验证结论必须有证据，失败与限制必须可见 | 已确认 | 缺少证据会让开发者无法判断结果可信度 |
| 平台范围 | 支持 Web、桌面端和移动端 UI 工程 | 已确认 | 平台规则不同，不能以单一平台假设覆盖全部场景 |
| 视觉风格 | 配色、字体风格和品牌一致性不纳入首版 | 明确排除 | 由 `ui-design-app` 或其他设计能力处理 |
| 无障碍 | 不进行完整无障碍专项审计 | 明确排除 | 首版聚焦布局和内容呈现；无障碍可作为后续独立范围 |
| 自动化集成 | 不要求自动触发、后台持续扫描或 CI 集成 | 明确排除 | 首版面向开发者主动调用 |

## 10. 外部依赖

- 代码分析依赖开发者提供或授权访问目标工程及必要关联代码。
- 截图分析依赖截图清晰展示目标区域和相关状态。
- 实际运行验证依赖目标工程可启动，且运行环境、数据与现有检查可用。
- 典型状态验证依赖工程具备相应状态或开发者提供可观察证据；无法触达时必须标记未验证。

## 11. 明确不做（Out of scope）

- 不选择、评价或迁移视觉风格，包括配色、字体气质和品牌一致性。
- 不替代 `ui-design-app` 的风格选择、风格确认和视觉系统迁移。
- 不进行完整无障碍专项审计。
- 不在截图单独输入时推断代码原因、提供修改建议或生成示例代码。
- 不自动接入 CI，不后台持续扫描，不自动触发 UI 检查。
- 不在增量模式修复目标及直接关联范围之外的历史问题。
- 不在全量模式修复未经开发者确认的分组。
- 不因改善布局删除必要功能、改变业务关系或压缩必要信息。

## 12. 假设、风险与未决问题

### 12.1 未验证假设

- 无已知未验证假设。

### 12.2 已知风险

- 代码作为预期基准可能无法代表未记录的产品意图；当代码与截图冲突时，本需求要求以代码为准并显式报告偏差，开发者需负责确认代码意图是否正确。
- Web、桌面端和移动端的布局语义与验证条件差异较大；首版必须允许“不适用”和“未验证”，避免跨平台误判。
- 全量审计范围可能很大；按区域或严重程度分组、逐组授权与验证用于限制上下文压力和变更风险。
- 信息层级与内容密度存在一定判断空间；只有能说明具体理解或操作影响的问题才应进入问题清单，避免把个人偏好当缺陷。

### 12.3 未决问题

- 无功能层未决问题。skill 的目录结构、参考文件、脚本、输出格式、平台识别方式和验证手段属于后续设计与实现阶段决策。
