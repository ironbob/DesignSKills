# 技术机制深度分析 Skill（tech-mechanism-analysis）— 功能需求文档

> 本文档只描述这个 skill「做什么功能」，不涉及交互/UI/技术实现（调用链解析方案、AST/LSP 选型、token 聚焦算法、可视化渲染库等一律记入「未决问题」留给后续技术设计）。
> 范围档位：**双模式完整版**（Lite：低交互成本的证据化 Markdown；Full：P0 全链路理解 + 双轴设计债审计带例子 + 双轨产物门禁；P1 多语言 + 机制类型模板库 + 跨段衔接缺陷 + 已知缺口；P2 链路可视化 + 代价量化）。
> 日期：2026-07-23。
> 注：skill 名称 `tech-mechanism-analysis` 为暂定，可在实现阶段调整。

---

## 0. 与现有 skill 的边界（关键，先读）

仓库已有三个分析 skill，本 skill 钉在它们都不占的位置——**单一技术机制的纵向全链路深挖 + 设计债审计**：

| 现有 skill | 它管什么 | 本 skill 的区别 |
|---|---|---|
| `arch-overview` | 画架构图 + 正向总评「整体设计好不好」 | 本 skill 不画整体架构图、不做整体总评；只深挖**一个机制**怎么跑通 |
| `arch-quality-eval` | 架构坏味道 + 要不要重构 go/no-go | 本 skill **不下 go/no-go**、不做模块级坏味道清单；只在该机制的**全链路**上找**设计债** |
| `code-analyze-business` | 一个**业务能力**的业务逻辑 + 反推需求 + 黑盒用例 | 本 skill 不看业务视角、不反推产品需求；只看**技术机制**怎么实现、哪里会卡住未来需求 |

**核心定义一（缺陷 = 设计债）**：本 skill 说的「缺陷」**不是正确性 bug**（不是「输入 X 会得到错误结果 Y」），而是**设计债 / 可演进性风险**——「因为设计问题，某些需求会很难实现 / 维护 / 扩展」。每个缺陷配一个「例子」= 一个**会变难的具体需求** + **当前设计哪里让它难** + **演进/松绑方向** + **代价/影响评估**。

**核心定义二（重点 = 技术细节，数值操作必给工作举例）**：本 skill 的**重点是技术细节**，不是泛泛讲流程。凡链路中涉及**数值计算**的环节（平滑 / 插值 / 缓动 / 变换 / 量化 / 滤波等），讲解时**必须给出真实数值的工作举例**：适度规模的示例数据（不太多、不太简）+ 逐步实际运算，且**运算逻辑必须与原代码一致**——为保证一致，必要时对代码做**等价翻译**（如转 Python 实际求值），翻译须忠实保留原逻辑。这一条既是讲解要求，也是「确实读懂了代码」的佐证。

## 1. 一句话目标

一个 skill，针对代码库里**一个技术机制**（如视频编辑器的关键帧、图片缓存、音视频同步、并发原语），先把它**全链路运作过程读透**（按机制类型套对应链路模板分段，如数据流型：产生→流转→处理→生效），讲清**技术细节与工作原理**（数值计算环节强制给真实数值的工作举例、运算逻辑须与原代码一致），再从**架构 + 逻辑**两个角度找出**会让未来需求难以实现/维护/扩展的设计债**（每条带「会变难的需求 + 为什么 + 演进方向 + 代价」的例子）。Lite 产出一份证据化 Markdown；Full 产出双轨报告（`analysis.json` 契约源 + `analysis.md` 人读渲染，过门禁），帮开发者**看懂这个机制怎么跑通 + 提前知道哪里会卡住未来需求**。

只回答两个问题：**这个机制是怎么从起点到最终效果全链路运作的**（理解）+ **它的设计会让哪些未来需求变难**（设计债审计，带例子）。**不回答**「整体架构好不好」「要不要重构」「业务需求是什么」「这里会不会崩」。

```
一个技术机制（名称 + 入口提示 + 根路径）──► [tech-mechanism-analysis] ──► Lite Markdown / Full analysis.json + analysis.md
                                                  │
                                                  ├─ 阶段一·理解：机制类型识别 → 套链路模板分段 → 逐段讲技术细节/工作原理（带证据）+ 跨段衔接 + 可视化
                                                  └─ 阶段二·设计债：双轴审计（架构 / 逻辑）→ 每条带「会变难的需求+为什么+演进方向+代价」例子
```

## 2. 目标用户

- **主要用户**：要对某个技术机制做**深挖 / 设计审视**的**开发者 / 技术负责人 / 架构师**——刚接手一个机制要读懂它怎么跑通的，或要评估它的设计会不会卡住后续需求，在动手改 / 排演进优先级之前先看清全貌与风险。
- **次要用户**：
  - 做**技术债盘点**的人（机制级设计债清单作为盘点输入）。
  - 写**技术文档**的人（全链路讲解 + 机制概述作为文档底稿）。
- **不是**目标用户：
  - 想找**正确性 bug / 崩溃复现**的人（本 skill 找设计债，**不找 bug**，见 out-of-scope）。
  - 想做**整体架构总览 / 画架构图**的人（用 `arch-overview`）。
  - 想做**架构坏味道 + go/no-go 重构决策**的人（用 `arch-quality-eval`）。
  - 想分析**业务逻辑 / 反推产品需求**的人（用 `code-analyze-business`）。
  - 想做**全 repo 架构巡检**的人（本 skill 单机制深挖，不批量盘点）。

## 3. 核心场景

- **接手读懂 + 风险预判**：开发者圈定一个技术机制（如「关键帧实现」）→ skill 全链路讲清它怎么从存储跑到画面 + 双轴指出哪些设计会卡住未来需求（带例子）→ 接手者既看懂机制，又提前知道演进风险点。
- **设计审视 / 演进规划**：评估一个机制好不好演进 → 双轴设计债清单（每条带「会变难的需求」例子 + 演进方向 + 代价）→ 作为重构 / 演进优先级排序的依据。
- **技术文档底稿**：用全链路分段讲解 + 机制概述作为该机制技术文档的起点（讲解与缺陷均带证据，可二次加工）。

## 4. 功能清单

### 模块 A：输入与范围界定

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 机制对象界定 | 接受用户指定的技术机制（名称 + 入口提示 + 根路径），圈定分析边界 | 能处理跨多目录/多文件的范围；报告明确列出本次覆盖的文件/调用链集合 |
| P0 | 机制类型识别 | 识别该机制属于哪类（数据流型 / 生命周期型 / 调用链型 / 状态机型…），决定套哪套链路模板 | 报告声明识别到的机制类型 + 判定依据；无法确定时显式标注并回退通用模板 |
| P0 | Full 范围确认（HARD-GATE） | Full 模式把「机制对象 + 类型 + 覆盖范围 + 一句话机制职责推断」呈现给用户确认；Lite 仅在存在无法消除且会改变分析对象的歧义时确认 | **Full 范围未经用户确认前，不进入链路追踪或缺陷审计**；确认动作写入 `scope_confirmations`。Lite 可直接追踪候选范围，但必须显式记录假设 |

### 模块 B：全链路分段追踪（阶段一 · 理解）

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 链路模板匹配与分段 | 按识别的机制类型套对应链路模板，把机制拆成若干段（数据流型：产生→流转→处理→生效；生命周期型：初始化→配置→运行→清理；调用链型：入口→委派→核心→副作用；状态机型：状态→转移→动作…） | 报告列出分段 + 每段对应的模板；某模板确不适用时显式声明原因，不得静默省略 |
| P0 | 逐段技术细节 + 工作原理 | 对每段讲清：做了什么、怎么实现、为什么这么设计、关键数据结构 / 算法 / 调用点（**数值计算环节必须带工作举例**，见下行） | 每段挂证据（file:line / 类 / 函数）；「怎么实现」与「为什么这么设计」都要有结论 |
| P0 | 数值操作工作举例（强制） | 对链路中涉及**数值计算**的环节（平滑 / 插值 / 缓动 / 变换 / 量化 / 滤波等），讲解时**必须**给出真实数值的工作举例：适度规模的示例数据（覆盖关键分支/边界，不太多、不太简）+ 逐步实际运算；**运算逻辑必须与原代码一致**，必要时对代码做等价翻译（如转 Python 实际求值）以保证一致 | 每个数值环节都有工作举例；示例数据非平凡（能体现操作行为，非 1+1）；运算步骤与代码逐对应、可回链 file:line；若做了代码翻译，显式标注翻译方式并声明忠实保留原逻辑 |
| P0 | 跨段衔接说明 | 讲清段与段之间怎么交接（数据格式 / 接口契约 / 时序 / 隐含约定） | 每个衔接点挂证据；显式标注衔接处的不写明假设（如「存储段写入格式 X，读取段假设格式 Y」） |
| P1 | 机制类型模板库 | 内置多套链路模板覆盖常见机制类型，可扩展 | 至少覆盖数据流 / 生命周期 / 调用链 / 状态机四类；模板可由用户补充扩展 |
| P2 | 链路可视化 | 用 Mermaid 把链路画出来（按机制类型选时序图 / 状态图 / 数据流图） | 图节点 / 流转步回链代码证据；生成器限制在安全可渲染子集；环境存在 `mmdc` 时做实际渲染，缺失时执行结构检查并登记缺口；信息不足时显式声明不出图 |

### 模块 C：双轴缺陷审计（阶段二 · 设计债）

> **铁律**：本模块找的是**设计债 / 可演进性风险**，**不是正确性 bug**。每条缺陷必须落到「让某个需求难实现 / 维护 / 扩展」。

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | 架构轴缺陷 | 找**结构性设计问题**（分层 / 职责边界 / 耦合 / 依赖方向 / 不恰当暴露）导致的「某需求难实现/维护/扩展」 | 每条挂证据（file:line）+ 指出所属链路段；结论指向「哪类需求会变难」 |
| P0 | 逻辑轴缺陷 | 找**算法 / 数据结构 / 状态机 / 数据流设计问题**（如单列表无法表达多轨道、状态机缺状态、算法假设过窄）导致的「某需求难」 | 每条挂证据 + 指出所属链路段；结论指向「哪类需求会变难」 |
| P0 | 缺陷例子（每条必含四要素） | 每个缺陷给出：①**会变难的具体需求** ②**为什么当前设计让它难** ③**演进/松绑方向**（真要做这需求，设计怎么改） ④**代价/影响评估**（改动面 / 涉及哪些段 / 风险） | 四要素齐全缺一不可；需求必须是具体可描述的（非「扩展性差」这种空话）；**不打严重度分级** |
| P1 | 跨段衔接缺陷专项 | 专项找段与段**衔接处**的设计债（数据格式假设不一致、接口契约脆弱、时序耦合、隐含约定未文档化）——全链路分析的高价值发现 | 衔接缺陷单列或明确标注「跨段」；每条同样带四要素例子 + 证据 |
| P2 | 代价量化 | 对每个缺陷给**改动面量化估算**（涉及哪些段 / 文件 / 模块、大致改动量级） | 估算有依据（基于已读代码事实），非拍脑袋；量级可解释 |

### 模块 D：产物生成（Lite 单轨 / Full 双轨 + 门禁）

| 优先级 | 功能 | 简述（做什么） | 验收标准（可判定） |
|--------|------|----------------|-------------------|
| P0 | Full 机器契约源 `analysis.json` | 把范围确认、机制类型、链路分段、工作原理要点和缺陷 findings（轴 / 所属段 / 四要素例子 / 证据）结构化为稳定契约源 | 字段稳定 + 带稳定 id；链路段与缺陷均挂证据；业界做法引用（若有）带 provenance + 核对状态 |
| P0 | 人读渲染 `analysis.md` | 渲染成人读报告：机制概述 + 全链路分段讲解（带 Mermaid 图）+ 架构问题章 + 逻辑问题章 + 已知缺口 | 含 frontmatter（机制名 / 类型 / 语言 / 日期）；Mermaid 可渲染；与 `analysis.json` 一致 |
| P0 | 门禁校验 | 交付前人工复核证据语义，再运行结构/枚举、文件与行号、md 渲染完整性、json↔md 一致性和**每条缺陷四要素齐全**校验 | 全部门禁过才交付；任一不过回到对应步骤修订；脚本不声称能自动证明证据语义或排除编造 |
| P1 | 已知缺口登记 | 把分析中的精度受限 / 信息不足 / 未能确认之处记入「已知缺口」 | 缺口显式列出，不混入正文当事实；多语言精度差异在缺口中体现 |

## 5. 明确不做（Out of scope）

- **不找正确性 bug / 不做 bug 复现**：缺陷 = 设计债，**不是**「输入 X → 错误输出 Y」的正确性问题；不预测崩溃、不给 bug 触发路径（那是别的工具 / 别的 skill）。
- **不下 go/no-go 重构决策**：只列设计债 + 演进方向，不下「要不要重构」的门禁判定（那是 `arch-quality-eval`）。
- **不做整体架构图 / 总评**：不画整体架构、不做整体设计档位评价（那是 `arch-overview`）。
- **不分析业务逻辑 / 不反推产品需求 / 不出黑盒用例**：只看技术机制怎么实现（那是 `code-analyze-business`）。
- **不下严重度分级**：缺陷不给 critical/major/minor 分级（用户明确要求）；演进优先级由代价/影响评估支撑，不做硬分级。
- **不做完整重构方案 / 迁移步骤 / 目标设计**：只给「演进/松绑方向」，不到方案级（那是重构阶段的事）。
- **不自动解析项目架构文档 / 复用代码内规约**（ArchUnit / dependency-cruiser 等）：本期不读取项目已有架构断言。
- **不做全 repo 批量巡检**：单次分析一个用户指定的技术机制，不做批量盘点。
- **不联网核实**：业界做法（若有引用）为 LLM 内置经验，声明未核对，不主动联网检索权威引用。
- **不做模块化度量纯数值**（LCOM/扇出/不稳定性等）：数值不当判定依据。
- **不主动修改代码**：只读分析 + 产出报告，不改任何源码。
- **不做 CI PR 自动卡关 / Code Review 场景**：定位机制深挖 + 设计审视，不做 CI 自动门禁。
- **不做评估结果历史对比 / 趋势**：单次分析即可。

## 6. 非功能约束

- **语言/技术栈**：**多语言通用**（Python / Go / JS / TS / 前端 / JVM / C++ 等）。调用链 / 数据流追踪精度**因语言而异**：有规范模块系统 / 类型系统的语言精度较高；靠目录约定 / import 启发的语言（如 Python、C++）精度受限。结论须按语言保守，并在「已知缺口」体现。
- **粒度**：单一技术机制级（跨多文件 / 调用链，范围可能偏大）——存在 **token 压力与噪音淹没关键链路**的风险，skill 必须有聚焦策略（只追与该机制相关的调用链 / 数据路径，不读无关代码，见未决问题）。
- **缺陷性质**：设计债 / 可演进性风险，**非正确性 bug**；禁止把「可能崩」「可能算错」当缺陷产出。
- **证据纪律**：链路每段、缺陷每条结论均回链代码（file:line / 类 / 函数 / 调用边），找不到的标 `⚠ 未确认` + 登记缺口，**禁止编造证据**。
- **图格式**：**Mermaid 为主**，内嵌 Markdown（终端 / GitHub / CI 可渲染、可 diff）。本期不产出 PlantUML/DOT 或位图导出。
- **业界做法来源**（若有引用）：LLM 内置经验，**不联网**；每条声明 provenance + 核对状态（未核对原文）。可信度透明但可能不精确/过时，须让用户知情。
- **数值举例的忠实性**：数值操作的工作举例**必须与原代码逻辑一致**；为保证一致，可对代码做等价翻译（如转 Python 实际求值），翻译须忠实保留原逻辑、不得简化掉影响结果的步骤；示例数据规模适中（覆盖关键分支/边界，不太多、不太简）。

## 7. 未决问题

- **机制类型模板的具体分段定义与判定标准**：数据流 / 生命周期 / 调用链 / 状态机四类各自的分段切法 + 「某机制属于哪类」的判据——需求层已给方向，具体分段与判据在 skill 设计时细化。影响：分段质量直接决定全链路理解是否完整。
- **多语言调用链 / 数据流追踪方案**（语言无关的目录/import 启发？各语言 LSP？AST？混合策略？精度如何按语言标注？）：属技术方案，超出需求澄清范围，留后续技术设计。影响：各语言上链路追踪精度与缺陷可信度。
