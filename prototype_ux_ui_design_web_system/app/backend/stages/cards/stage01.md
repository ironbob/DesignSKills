# 阶段 1：需求消化（任务卡）

## 目的

把需求文档读成**设计视角的理解**，产出三样东西让产品方拍板。本阶段不打开任何画布。

## 输入

`00-requirement.md`（需求文档）。功课义务：凡问题清单里能靠查证现有产品/代码回答的，先查再问（查不到才进问题清单，并声明"功课做了但查不到"）。

## 产出与模板（写入 `01-需求消化.md`）

1. **一句话重述**：帮谁、在什么场景、完成什么（设计视角，不是复述功能）。
2. **Job Stories**：每个核心场景 ≥1 条，格式 `当【触发情境】时，我想【意图】，以便【收益】`，每条标人像。专家会补 PRD 没写但体验关键的约束故事（如"设好后双手离开设备"）。
3. **设计张力**：3–6 条专家第一直觉（如"核心屏的版式逻辑像提词器不像 App 页"）；若存在上一轮产物，其审计教训制度化为张力。
4. **问题清单**：
   - 阻塞性 A-x（不答没法画 IA/核心屏），每条注"为什么阻塞"；
   - 非阻塞 B-x（带默认假设，不清空即生效）。
   - 功课声明：哪些问题本可自查、查证结果如何。
5. **设计层成功标准**：≤6 条，区别于功能验收（可度量：距离/时长/触控次数/无死角矩阵等）。
6. **决策台账骨架**（文件尾部，全流程追加）。

## 决策数据（另写 `.stage1-questions.json`，供界面问题单消费）

```json
{
  "blocking": [
    {"id": "A-1", "text": "问题", "situation": "为什么阻塞/影响范围", "scope": "全局|S? 屏",
     "options": [
       {"label": "选项A", "recommend": true,  "claim": "主张", "consequence": "选它会怎样（反面后果）"},
       {"label": "选项B", "recommend": false, "claim": "主张", "consequence": "选它会怎样"}
     ]}
  ],
  "defaults": [
    {"id": "B-1", "text": "默认假设问题", "value": "默认生效的假设"}
  ],
  "success_criteria": ["可度量标准", "…"]
}
```

硬要求：每个阻塞问题 ≥2 个选项；恰好一个 `recommend: true`；每个选项三件套齐（claim/consequence 忘一即 gate 不过）。

## 完成标志

阻塞问题全部被回答并进台账；每个核心场景有 job story；成功标准每条可度量。

## 工具化要点（网页工具映射）

- AI 任务：读需求文档 → 生成 memo 草稿（stories/问题清单/张力/标准）。
- 界面：问题单表单（A-x 必答阻塞提交，B-x 折叠默认）；成功标准清单可勾选编辑。
- 台账落库：每条回答/拍板 = 一条决策记录（阶段、问题、答案、时间）。
- gate：未决项覆盖检查；A-x 全答才放行阶段 2。
