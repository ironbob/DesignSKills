# 01-写作情境

## 一句话论点（候选，待拍板）

- **候选 A（推荐·整体切换）**：Q4 将本地数据层从 Core Data 整体切换为 GRDB.swift 并引入自研增量同步引擎——真机实测五项核心指标全面改善 17–65%，同步 POC 冲突自动解决率 100%，代价是 7 周排期和一个靠 Repository 层隔离的第三方依赖风险。
- **候选 B（分期）**：数据层问题真实但应分两期决策：一期只换存储（GRDB，Q4），同步引擎二期单独评审——本方案信息密度过高，一次评审决策半径太大。
- **候选 C（不切换）**：暂不换框架，围绕 Core Data 做性能专项（批写入、迁移脚本化）以最小改动缓解卡顿，把重构窗口留给更晚的时点。

拍板：**候选 A**（素材本身是完整选型+POC+排期的成案，评审目标就是为整体方案放行；B/C 与素材意图不符，B 可作为评审会上的备选议题而非文档论点）。

## 写作张力（专家第一直觉）

1. **评委带着"为什么不用官方方案"进场** → 对比节必须先发制人，落选理由逐条给证据（SwiftData 的三条硬伤来自预研不是印象）。
2. **投屏 + 细读混合场合** → 每节独立成立、一屏一论点；性能数据一图一结论，图题即数字结论。
3. **2000 字硬约束** → 论证用文字、数据全进图表/表格；对比要点写"为什么否"不写百科式介绍。
4. **预研数字是全文弹药库** → 口径（机型/系统/构建/数据集）必须随图可见，防"数字哪来的"质疑。
5. **风险要主动示弱** → 社区规模风险不回避，给出 Repository 隔离的工程兜底，比藏起来更可信。

## 文种判定

**技术方案（评审会成案放行型）**。叙事模板：问题 → 结论先行 → 对比论证 → 证据（预研）→ 风险与计划。硬约束映射：五要素 → 五节（背景与目标 / 选型结论 / 候选对比 / 预研数据 / 风险与计划），外加开篇结论摘要，共 6 节左右。

## 成功标准（≤5 条，可判定）

1. 评委读完能一句话复述论点（切换 GRDB + 自研同步，实测改善 17–65%，7 周完成灰度到全量）。
2. D-1 ~ D-7 每条都有明确章节回答（阶段 3 gate 校验覆盖）。
3. 成稿每个数字 ⊆ 02-事实台账，图表口径可见。
4. 正文 ~2000 字（±10%），含数据表格 ≥2 张、数据图 ≥1 张。
5. 渲染产物过 check_doc --md 七查 + build 0 退出 + DOM 实测。
