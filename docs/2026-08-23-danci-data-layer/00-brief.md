## 素材（用户提供，全部数字的唯一来源）

### 背景
- 现状：数据层基于 Core Data（iOS 14 时代搭建）
- 诱因：离线刷题、多设备同步、SRS（间隔重复）调度加入后，出现**写入卡顿与迁移困难**
- 目标：替换本地存储框架 + 引入同步引擎，支撑未来 2 年功能演进
- 约束：iOS 16+ 起步、团队 Swift 为主、离线优先架构

### 选型结论
| 模块 | 选定 | 落选 |
|---|---|---|
| 本地存储 | GRDB.swift 6.x | SwiftData、Core Data（保留现状） |
| 序列化 | Codable + JSON | Protobuf |
| 数据同步 | 自研增量同步（`updated_at` 游标） | CloudKit、CRDT |
| 响应式绑定 | Combine + GRDB ValueObservation | 手写通知中心 |

### 落选理由
1. SwiftData：SwiftUI 亲和度高，但 `@Model` 非 Sendable 限制多线程写入、iCloud 同步行为黑盒、无法精细控制迁移
2. CloudKit：免运维但冲突策略不可控、无法支持 Android 端未来规划
3. Protobuf：序列化性能优（包体积 -38%），但双端 schema 维护 + 学习成本高于收益

### 预研性能数据（iPhone 13 真机，iOS 17.4，Release 构建；数据集：5 万单词 + 120 万条学习记录）
| 指标 | Core Data | GRDB | 变化 |
|---|---|---|---|
| 冷启动首次加载 | 820 ms | 310 ms | -62% |
| 批量写入 1 万条 | 4.6 s | 1.8 s | -61% |
| 复杂查询（SRS 调度） | 96 ms | 34 ms | -65% |
| 内存峰值 | 210 MB | 148 MB | -30% |
| 数据库文件体积 | 86 MB | 71 MB | -17% |

### 同步引擎 POC
- 断网 24h 累积 2,300 条本地操作，恢复联网 **3.2 s** 完成全量上行合并
- 冲突率 0.4%，均按「服务端时间戳优先」自动解决
- 压测：模拟 10 万 DAU，同步接口 P99 480 ms、错误率 0.02%

### 风险与计划
1. 风险：GRDB 社区规模小于 Core Data → 封装 Repository 层隔离依赖，预留更换成本
2. 迁移：双写灰度两周 + 全量数据校验脚本，回滚窗口 7 天
3. 排期：Q4 第 1–2 周 Repository 封装；第 3–6 周灰度迁移；第 7 周全量
