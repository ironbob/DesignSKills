# 架构设计质量量规

以《代码大全 2》的复杂度管理与构造设计思想为指导，只评价模块级职责、边界、依赖和变化传播；不检查语法、编译错误、语言技巧或 lint。语言工具只提供证据。

## 使用规则

1. 六轴全部给出 `concern`、`no-material-concern` 或 `inconclusive`。
2. 先确认架构角色与变化原因，再判断症状；目录名、行数、依赖数只能定位候选。
3. finding 必须回链源码事实，并分别记录影响严重度与证据置信度。
4. 没有充分覆盖时写 `inconclusive`，不得用“未发现”暗示已经排除问题。

## 六个设计轴

| 轴 | 核心问题 | 可成立的证据 | 常见症状 |
|---|---|---|---|
| `complexity-management` | 设计是否把复杂度封装在少数清晰概念中，还是制造额外协调负担？ | 一条主流程需理解多个无关职责；不必要的跳转/代理；中心类承担多类决策 | God Class、无收益间接层、控制中心膨胀 |
| `responsibility-cohesion` | 模块内元素是否因同一业务目的而变化？ | 一个类有多种无关变化原因；同一概念散落在无关模块 | God Class/Package、职责混杂、特性依恋 |
| `coupling-dependency-direction` | 依赖是否必要、单向、可解释，并指向稳定边界？ | 循环边；高层掌握底层细节；跨边界调用造成连锁变化 | 循环依赖、跨层调用、不稳定依赖 |
| `information-hiding` | 易变化决策是否藏在稳定接口后，接口是否只暴露必要能力？ | 内部实现成为公共契约；调用方需要知道实现步骤或数据布局 | 不恰当暴露、宽接口、实现泄漏 |
| `abstraction-consistency` | 同一模块/流程是否处在一致抽象层级？ | 业务策略与存储、协议、UI 机制混在同一职责单元 | 胖控制器、中间人过载、策略/机制混杂 |
| `change-isolation` | 一类变化能否局部完成，还是向多处传播？ | 同一变更主题反复协同修改多个无关单元；一个单元承受多类变化 | 霰弹式修改、发散式变化、平行继承 |

## 误报保护

- 大类只有在职责确实不相关且变化原因不同后，才判 God Class。
- 组合根、注册器、门面可合理依赖多个组件；高扇出本身不是 finding。
- 转发层若隔离协议、权限、事务或外部系统变化，不判无收益中间人。
- 公共方法只有在泄漏易变实现或扩大非必要兼容面时，才判暴露过度。
- 跨目录依赖只有在双方架构角色和方向已确认后，才判跨层。
- Git 共变更只作变化传播线索；提交不足时把 `change-isolation` 标为 `inconclusive`，不凭当前目录结构编造历史结论。

## 架构可理解性

可理解性是六轴的综合结果，不再作为独立 finding 轴。报告用一句话说明：主要职责能否快速复述、关键依赖是否可解释、抽象层级是否一致。命名只在误导架构职责时作为佐证，不评价命名格式。

## C++ 与 JVM 的一致性

相同职责、边界和依赖形态应得到相同原则类别与影响等级。LSP、Clang AST、import、include 或文本搜索只影响 `confidence` 与覆盖缺口，不改变架构原则。
