# 架构事实取证协议

## 目标事实

- 模块/职责边界与稳定接口。
- 内部依赖边、调用方向和循环候选。
- 易变化实现是否泄漏到调用方。
- 策略与实现机制是否混在同一职责单元。
- Git 可用时的变化传播线索。

## 流程

1. 运行 `scan_architecture.py --output <scan.json>`，完整事实只落磁盘。
2. 用 `query_scan.py` 查询热点、循环或特定类型/文件。
3. 探测 LSP；可用时补强关键引用/调用，不可用时使用文本索引。
4. 读取候选附近最少源码，确认双方架构角色和变化原因。
5. 将实际范围、索引、精读和语义解析文件分别写入 coverage。
6. 不能复核的候选用 probable/hypothesis；可能隐藏阻塞项时把相关设计轴标 inconclusive。

扫描器不判坏味道。数值、路径、命名、include/import 和 Git 共变更只是线索；finding 必须基于职责、边界、依赖或变化传播的语义事实。

## 大模块

完整索引覆盖整个确认范围，不截断依赖事实；模型 Context 只读取：

1. 循环候选与最高热点；
2. 两个分析轨请求的相关子图；
3. 最终 finding 使用的源码片段。

抽样精读必须如实进入 `coverage.inspected_files`。范围大但精读不足以排除 critical 时，输出 inconclusive，而不是乐观 go。

## 防臆造

- 证据必须回链真实 file:line。
- 工具命中与注释不等于架构事实，必须阅读代码确认。
- Git 不可用时不编造历史变化模式。
- 工具降级写入 coverage/omissions，不把工具能力缺口当架构 finding。
