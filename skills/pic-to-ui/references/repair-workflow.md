# 现有 UI 的差异审计与修复

本流程用于“已有代码和可见 UI，但与参考截图不一致”。目标是**修复现有实现**，不是重新生成一份平行页面。

## 1. 定位现有实现

从屏幕入口向下读取：路由/导航入口 → 页面容器 → 子组件 → 主题和 token → 图标/位图资源 → 状态与数据绑定 → 相关测试。记录：

- 哪些文件真正控制目标屏；
- 哪些样式来自共享组件或主题；
- 哪些交互、状态、导航和业务绑定必须保持；
- 当前工作树中哪些改动属于用户，不能覆盖。

不要只搜页面文件里的数字。视觉根因经常位于父容器、共享 modifier/style、系统 inset、主题 token 或资源映射。

## 2. 建立可比基线

优先使用工程现有的 preview、模拟器、设备截图或 screenshot test。尽量固定：

- viewport/设备型号与方向；
- scale、主题、动态字体、语言和 locale；
- 系统栏/安全区、键盘、滚动位置；
- 数据 fixture 和交互态。

保存当前渲染为 before 证据。工具链不可用时，记录具体失败原因；不要为了拿截图擅自搭建新工程或大改构建配置。

## 3. 按层比较并诊断根因

按以下顺序比较，避免先调细节后推翻：

1. `structure`：区域顺序、嵌套、滚动容器、对齐、层叠、安全区。
2. `entry`：按钮、Tab、菜单、可点图标、链接是否存在且位置正确。
3. `dimension`：容器比例、宽高、padding、gap、圆角、字号与行高。
4. `style`：字体字重、颜色、描边、阴影、背景和透明度。
5. `icon/bitmap`：资源、缩放模式、裁切、tint 和语义。
6. `state`：选中、禁用、空、加载、错误及截图 fixture。

为每个差异关联 blueprint id，并写“证据 → 根因”。例如：

- 好诊断：`N3` 宽度偏小，因为父容器仍应用通用页面 24dp horizontal padding。
- 坏诊断：卡片看起来不对，改一下 padding。

若多个症状来自同一根因，分别登记 mismatch，但共享同一诊断和修改锚点，便于逐项验证。

## 4. 最小化修复

- 优先调整已有约束、token、style 和资源映射。
- 只在目标布局无法由现有结构表达时替换局部组件。
- 保留交互 handler、状态源、导航、数据流、accessibility 标识和测试定位符。
- 避免针对单张截图堆叠绝对位置或 magic number；在基准设备对齐，同时保留工程原有响应式行为。
- 修改共享 token 前检查其他消费者；影响超出目标屏时，优先创建局部 override 或向用户标红风险。

## 5. 小步渲染与关闭

按“上游布局 → 组件尺寸/样式 → 资源 → 状态”分批修改。每批：

1. 运行最窄相关构建或测试；
2. 重新渲染同一 fixture；
3. 与参考截图及 before 证据比较；
4. 更新 mismatch 的 status、resolution 和 verification；
5. 仍有残差则继续迭代，不提前标 `resolved`。

若不能生成 after 渲染：可以修复代码和回归行为，但纯视觉 mismatch 必须 `flagged` 为未验证。静态代码检查不能证明颜色、间距或整体观感已匹配。

## 6. 回归范围

至少检查：

- 目标屏能编译/预览；
- 原有点击、导航、输入和状态切换仍连接原处理逻辑；
- light/dark、动态字体或不同尺寸若受改动影响，没有明显退化；
- 共享组件/token 的其他消费者未被意外改变；
- 用户原有工作树改动未被覆盖。

无法执行的项目写进 `report.md`，不要省略。

## 7. 报告格式

`report.md` 至少包含：

- 模式与目标屏；
- before/after 环境和证据；
- 已修复 mismatch（id、根因、代码锚点、验证结果）；
- flagged mismatch（原因、影响、下一步）；
- Gate 结果；
- 运行过的构建/测试及未运行项；
- 实际修改文件范围和潜在回归风险。
