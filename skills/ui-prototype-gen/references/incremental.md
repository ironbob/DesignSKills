# 增量开发 / 已有工程续作（任务卡）

适用：在**已完成或进行中**的项目上提交一份新需求/需求变更。初始九阶段流程不变；本卡是其受控扩展。
网页工具映射：阶段 0（影响分析）任务卡快照 = 工具内 `stages/cards/stage00.md`，L2 判据卡 = `rubric-00.md`。

## 1. 基线输入（建 revision）

- 必须指认 `base_snapshot_id`（基于哪个已确认快照；默认最新——已完成项目即最终交付快照）。
- 工作区 = 基线快照整树副本 `revisions/<id>/`：继承基线 `09-spec.md`、`06-tokens.json`、`07-hifi/`、03（IA+盘点）、02（流程）、01（历史决策台账）；新需求正文与变更说明写 `00-change-request.md`。
- **原项目工作区与全部历史快照只读**——增量产物只写 revision 工作区，合并是唯一带回项目的路径。

## 2. 阶段 0：影响分析（先分析，不重跑）

输入：基线契约三件套 + 03 IA + 01 台账 + `00-change-request.md`。
产出（结构化、可程序消费）：`00-impact.json` + `00-impact.md`：

```json
{
  "summary": "一句话变更摘要",
  "pages": {
    "added":    [{"page_id": "S6", "name": "成就页", "reason": "为何新增、挂在哪"}],
    "modified": [{"page_id": "S3", "level": "content|component|layout|style", "reason": "改了什么"}],
    "removed":  [{"page_id": "S9", "reason": "为何删除、入口与流程如何收口"}]
  },
  "flows": ["受影响任务流（02 的 F# + 一句说明）"],
  "navigation": ["受影响导航"],
  "states": ["受影响状态"],
  "shared_change": {"tokens": false, "components": false},
  "regression_pages": ["回归验证但无需重做的页面"]
}
```

硬规则：修改/删除页必须在基线盘点中；新增页不与基线冲突；导航/流程/共享 token/组件任一受影响 → `regression_pages` 必须列关联页面与主流程页；拿不准级别保守取高一级。**重跑阶段与回归终值由程序确定性推导（见 §3），不自行编造执行计划。**

## 3. 变更分级 → 重跑范围（确定性映射）

| 分级 | 重跑阶段 | 理由 |
|---|---|---|
| content | 7, 9（状态有变 +8） | 仅页面规格/文案与必要状态 |
| component | 6, 7, 9 | 更新设计系统后重出受影响页面 |
| style | 6, 7, 9 | 更新 token 后重出受影响页面 |
| layout | 4, 7, 8, 9 | 必须回阶段 4，并同步后续相关产物 |
| 新增页面 | 2, 3, 4, 7, 8, 9 | 更新流程/IA/盘点 + 线框/高保真/交互/crit/规格 |
| 任何变更 | 9 恒在 | 最终规格必须自包含 |

## 4. 增量执行约束

- 只处理受影响页面与本阶段产物；未受影响页面/产物继承基线，不重做不改动。
- **质量 gate 一项不减**：增量阶段的 L1 gate / L2 评审判据与初始九阶段完全一致；不允许为"增量"跳过 L1、L2 crit、状态覆盖和最终规格自包含性。
- 每个增量阶段过双层 gate 后仍要人审拍板（增量变更一律显式确认，不引入 auto 代批）。
- 回归页 = 基线产物保留 + 对照检查（不重做）；回归结论写入最终规格。

## 5. 合并与契约更新

- revision 全部受影响阶段完成 → 产出**新的完整契约**（09-spec + 06-tokens + 07-hifi）。
- 09-spec 附「变更记录」节，五要素不可缺：**基线（快照号+旧版本）、变更摘要、受影响页面（增/改/删）、回归结果、版本号**。
- 合并 = 拷回项目工作区 + 落项目快照（reason 注明 revision 出处）+ 契约版本 v+1 + 页面注册表收口（新增/修改/删除落 lifecycle）。
- 历史快照与被合并的 revision 工作区永久保留可追溯；回退用快照恢复（先保全当前状态），不删历史。

## 完成标志（L1 gate）

影响分析 JSON 结构合法（三组页面、级别合法、页面存在性对得上基线、交叉影响带回归范围）；执行计划可由程序推导；增量阶段产物过对应阶段 gate。

## 反模式（增量专属）

| 反模式 | 正确做法 |
|---|---|
| 收到新需求整轮重跑 | 阶段 0 先分析，确认范围后只重跑受影响阶段 |
| 为省时间跳过 crit/状态覆盖 | gate 一项不减；content+状态变更也必须过 8 |
| 直接改基线工作区或快照 | 只写 revision 工作区；合并是唯一带回路径 |
| 影响分析夸大范围（多列页面/级别虚高） | 逐条对照新需求；拿不准取高一级但必须给理由 |
| 新增页面不动 IA/流程 | 2/3 必跑，导航入口与闭环检查同步 |
