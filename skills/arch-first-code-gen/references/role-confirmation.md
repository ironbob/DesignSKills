# 角色确认法（模块 B 核心）

> 配合 `arch-first-code-gen` 的 Checklist 第 3 步。这是 skill 的**心脏**：参考按栈标准做法库 + 设计原则，默认通过**几轮讨论**确认角色（分层 + 领域）/ 职责 / 依赖，产出「角色职责清单」。**未完成确认审查不编码（HARD-GATE）：用户明确要求省略中间确认时，保留完整审查与清单，由 skill 自动确认并留痕。**
>
> 模块 B 先定角色/职责/依赖/信息隐藏边界，再于编码前冻结关键跨角色接口；模块图与完整渲染留给模块 D。

## 一、确认什么（PRD §4-B）

每轮讨论收敛到一份「角色职责清单」，每行：

| 角色 | 类型 | 层 | 领域角色 | 职责（单一） | 隐藏秘密 | 变化触发器 | 数据所有权 | 依赖 | 业界做法依据 | 设计原则 |

- **类型**：分层角色（layer）/ 领域角色（domain）。
- **层**：controller/service/repository/domain/infrastructure/...
- **领域角色**：aggregate/entity/value_object/domain_service/domain_event/null。
- **职责**：动词开头，单一（SRP）。
- **依赖**：依赖哪些角色（依赖方向，DIP）。
- **业界做法依据 + 设计原则**：PRD 强制——每角色说得出「来自什么业界做法」「依据什么原则」。

## 二、确认流程（默认几轮讨论；可自动确认）

1. **从标准做法库取候选**：按 `standard-practices/README.md` 的栈映射加载对应文件，把角色目录当候选池；涉及 UI 时同时加载 `ui-architecture-policy.md`。
2. **逐条判适用性**：对照具体需求，每个候选角色判「**适用 / 调整 / 不适用（+理由）**」。只采用过判断的，不照搬。
   - 例：需求是纯 CRUD 无复杂领域逻辑 → 判「不用聚合根，只 controller/service/repository，理由：无跨实体一致性约束」。
3. **定职责 + 依赖**：每个采用的角色写一句话职责 + 依赖谁；检查依赖方向单向（架构门可查）、单一职责（SRP）。
4. **分层 + 领域两类都过**：先过分层角色，再过领域角色；任一类不用要说明理由，不静默漏。
5. **标注依据**：每角色填 `industry_basis` + `design_principles`（从 `design-principles.md` 取）。
6. **检查信息隐藏**：每角色写 `hidden_secret/change_triggers/data_owned`。没有清晰秘密则考虑合并；隐藏多个无关秘密则拆分。

UI feature 在角色清单前先定 `ui_architecture`：当前/目标模式、状态所有者、MVVM 适用性、迁移影响、影响范围和确认状态。适用且影响可控时优先 MVVM；纯展示或已有清晰替代模式不创建空 ViewModel。新引入 MVVM 且迁移影响为 `high` 时，向用户呈现范围/收益/风险/小改替代方案，`migration_confirmation=pending` 并停止编码；只有用户明确同意后才能继续。自动确认模式不覆盖这一项。

用户明确要求无需中间确认时，不跳过以上 1–5 步，也不简化清单字段；改为一次性完成候选判定、依赖审查和清单产出，并将结果记为“自动确认”。须在契约 `gate.notes` 与架构文档复核结论中注明确认方式、关键假设和取舍理由。需求或栈存在实质歧义时，自动确认不能替代必要的用户输入。

角色确认前先按 `architecture-design-method.md` 选择 profile、写质量属性并比较候选方案。模块 B 仍不设计私有方法；角色确认后必须在编码前补齐 `interfaces[]`，不能把关键接口推迟到编码后。

## 三、收敛与回退（PRD 未决项的 skill 层约定）

- **收敛信号**：角色清单稳定（增删趋于 0）、依赖方向无环、每角色有依据 → 默认呈现完整清单请用户确认；自动确认模式下记录同一份清单及取舍后继续。
- **几轮的边界**：通常 2-4 轮足够；超过仍未收敛，说明需求边界可能不清，提示回去收紧范围（模块 A）。
- **用户否决某角色**：回到第 2 步重判——否决后其职责归谁？依赖怎么调整？更新清单重确认。
- **不设计私有实现细节**：模块 B 先定角色边界，再冻结关键跨角色接口；模块图仍在模块 D 统一生成。

## 四、与业务流程梳理的衔接（P1）

角色确认基本完成后，按 `business-process.md` 梳理**主流程 + 异常分支**（P1），为模块 D 流程图 + 模块 E 覆盖门打底。流程每步要能映射到参与的角色。

## 五、角色职责清单 → 契约源

确认后，清单直接映射到 `design-contract.json` 的 `roles[]`（见 `design-contract-schema.md §三`）：每个角色一个对象，含 id(`ROLE-[LD]<n>`) / name / role_kind / layer / domain_role / responsibility / depends_on / industry_basis / design_principles / code_units。

> `code_units`（代码文件路径）在模块 C 编码后回填；模块 B 阶段可留空或填预期路径，交付前应真实存在，`validate_gate.py` 可辅助发现悬空角色。

## 六、反模式

| 反模式 | 正确做法 |
|---|---|
| 凭「感觉要个 Service」设角色 | 每角色标注业界做法依据 + 设计原则 |
| 只设计分层角色，漏领域角色 | 分层 + 领域两类都过，不用说明理由 |
| 角色还未稳定就设计大量方法 | 先稳定角色边界，再只冻结关键跨角色接口；私有方法留给构造期 |
| 角色职责写成「管理订单」（含糊） | 动词开头、单一：「接收下单请求、校验入参、编排」 |
| 依赖方向成环 / 下层依赖上层 | 单向、指向稳定方（DIP/dependency_direction） |
| 业界依据写成「符合业界标准」（空泛） | 具体到「MVC Controller（Spring @RestController）」「DDD 聚合根」 |
| UI 不看现状就统一套 MVVM | 先评估当前模式与 feature 复杂度；适合时优先，不适合时说明理由 |
| 用自动确认跳过高影响 MVVM 迁移确认 | 必须等待用户明确同意并记录 `user_confirmed` |
