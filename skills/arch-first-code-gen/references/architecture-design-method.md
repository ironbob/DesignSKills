# 构造期架构设计方法

> 在模块 B 使用。目标不是一次猜中架构，而是以与风险相称的成本，比较方案、隐藏复杂度、明确边界，并把高风险假设在编码前或编码早期验证掉。

## 一、选择设计强度

先根据 feature 的规模、寿命、可靠性、团队协作面和技术不确定性选择 `design_profile`：

| profile | 适用条件 | 最小产物 |
|---|---|---|
| `light` | 局部、低风险、沿用成熟模式、无公共接口变化 | 1 个方案、关键角色、存在跨角色调用时至少 1 个接口契约、验证命令 |
| `standard` | 默认；跨多个角色、有业务流程或公共边界 | 至少 2 个候选方案、质量属性、接口/数据/错误契约、独立复核 |
| `high_risk` | 高可靠性、跨上下文、并发/事务复杂、技术陌生或迁移影响大 | `standard` 全部内容 + 风险 spike/原型结果 + 用户或同行明确评审 |

不要用“大 feature 才需要设计”判断强度。一个很小但会处理资金、权限或不可逆数据的 feature 仍是 `high_risk`。

## 二、先声明质量属性，再比较方案

把影响设计的质量属性写成可判断场景，而不是空泛形容词：

| 字段 | 示例 |
|---|---|
| `name` | reliability / maintainability / latency / security / testability |
| `priority` | high / medium / low |
| `scenario` | “仓储超时后，重复请求不得创建第二个订单” |
| `acceptance` | “同一 idempotency key 只产生一个聚合；错误可重试且有审计日志” |

`standard/high_risk` 至少比较两个真正不同的候选分解。每个候选写清：摘要、优点、代价、风险。选择理由必须引用质量属性和现有仓库约束；不得因为“业界常用”直接胜出。

同时做两次检查：

1. **自顶向下**：从业务流程、质量属性和系统边界推导角色。
2. **自底向上**：从现有代码、框架约束、数据模型和可复用能力反查方案是否落地。

## 三、用信息隐藏定义角色

每个角色除职责外，还要回答：

- `hidden_secret`：它隐藏哪个容易变化、困难或不稳定的决定？
- `change_triggers`：哪些变化应只影响该角色？
- `data_owned`：它拥有或维护什么数据/状态？没有则明确写“无持久状态”。

如果角色没有可说明的职责边界或隐藏秘密，考虑合并；如果隐藏了多个互不相关的秘密，考虑拆分。类、模块和例程首先是降低复杂度的工具，不是为了凑层次。

## 四、编码前冻结最小接口契约

角色确认后、编码前，为跨角色关键调用写 `interfaces[]`。至少包含：

- provider / consumers；
- 输入与输出；
- 前置条件、后置条件和必须保持的不变量；
- 错误类型、传播/转换策略和调用方责任；
- 数据所有权、可变性和生命周期；
- 事务、幂等、并发、取消边界；不适用时明确写 `not_applicable`。

接口契约只冻结边界，不提前设计每个私有方法。若接口仍无法说清，说明角色划分尚未达到“实现趋于显然”的程度，应回到候选方案或角色确认。

## 五、验证风险与设计假设

`high_risk` 或存在技术不确定性时，用最小 spike 回答一个具体问题，例如：框架生命周期是否支持取消、事务是否能覆盖外部调用、SDK 是否提供幂等键。spike 是验证证据，不直接当生产实现；记录问题、方法、结果和结论。

在 `verification.checks[]` 中把关键质量属性、接口不变量和异常路径映射到验证方式：

- `existing_test`：运行仓库已有测试；
- `new_test`：在本 feature 范围内新增必要测试；
- `static_check`：类型/依赖/契约校验；
- `manual_review`：只能人工或语义复核的事项。

本 skill 不负责建立通用测试框架，但不能因此跳过验证。交付前必须实际运行可运行的验证命令；无法运行的项目写入 `unverified`，并降低结论置信度。

没有 Maven/Gradle、测试框架或项目脚手架时，不要仅为本 feature 擅自引入构建系统。优先使用栈原生最小 harness（例如 JVM 的 `javac` + 可执行断言类、Python `unittest`、Swift Package 现有 test target）验证关键不变量；是否引入新工具属于独立架构/工程决策。

自动确认不能替用户决定会改变公开业务语义的歧义，例如“相同幂等键但载荷不同是冲突还是首写获胜”“库存容量不足时拒绝还是排队”。这类问题必须回模块 A 请求明确输入；技术命名、局部拆分等可逆选择才可自动确认。

## 六、评审与回退

- `light`：允许自审，但要记录关键假设。
- `standard`：至少做一次独立复核；可由用户、同行或新视角语义复核完成。
- `high_risk`：必须由用户或同行确认选型和 spike 结论。

编码发现边界不合理时允许回到模块 B。设计契约是当前最佳假设，不是禁止演化的冻结文档；任何变化都要同步契约、代码、文档与验证证据。
