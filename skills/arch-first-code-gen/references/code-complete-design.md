# 《代码大全2》架构与设计准则

在方案阶段读取。本文件用可执行的原则 ID 概括 *Code Complete, Second Edition* 的设计思想；不替代原书，也不要求机械套用模式。

## 主准则

| ID | 方案阶段必须回答的问题 |
|---|---|
| `cc_manage_complexity` | 是否把人一次需要理解的状态、分支和协作方压到可控范围？ |
| `cc_information_hiding` | 每个角色隐藏什么易变决策，调用方是否无需知道其内部细节？ |
| `cc_lean_design` | 是否只保留当前质量属性和风险真正需要的角色、接口和扩展点？ |
| `cc_loose_coupling` | 依赖数量、可见性、方向和交互强度是否足够小？ |
| `cc_strong_cohesion` | 一个角色内的操作是否服务同一目的，变化原因是否集中？ |
| `cc_class_contract` | 类型是否维持有效状态，接口是否最小且语义稳定？ |
| `cc_design_for_test` | 关键行为能否在较少环境依赖下观察、控制并验证？ |

先用 `cc_manage_complexity` 和 `cc_information_hiding` 划边界，再用精简、耦合、内聚、类型契约和可测试性复核。SOLID、DDD、分层架构及仓库既有模式作为次级工具：只有能改善已声明质量属性、保护不变量或降低真实风险时才使用。

## 方案输出要求

- 在 `guidance.primary_source` 记录 `Code Complete, Second Edition`。
- 每个角色的 `design_principles` 至少引用一个 `cc_*` 原则，并说明到具体职责、秘密或依赖。
- 候选比较必须包含复杂度成本；新增抽象需要对应真实变化源或风险。
- 设计由自顶向下流程分析与自底向上仓库约束共同校验；无法确定的高风险点先做最小 spike。
- 不以类数、层数或模式数量代表质量；优先选择更容易正确实现和验证的最简单方案。

## 失效信号

- 多个角色共享同一秘密，或一个角色同时隐藏多个无关变化源。
- 接口暴露调用方不需要的方法或内部数据结构。
- 为假想扩展创建通用框架，增加理解和验证成本。
- 领域模型没有真实不变量却引入聚合/领域服务。
- 方案只能解释“用了什么模式”，不能解释为什么更可靠、更易验证。
