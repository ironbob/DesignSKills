# 领域分析：用专业与业界做法审视需求

> 配合 clarify-requirements skill 的"领域分析"步骤。
> 目的：在取得目标用户、核心结果、主要场景和产品阶段等最小上下文后，用领域知识与业界做法识别需求中的**盲区**和**风险**，避免盲目接受用户表述，也避免脱离上下文套用竞品。

---

## 一、为什么需要领域分析

用户的一句模糊需求往往只包含"他想到的"，而漏掉了该领域**几乎所有产品都有的标配**，也可能踩中**常见的坑**。若直接问"你还想要什么"，用户多半答不上来——他不知道自己不知道。

领域分析的价值是：在已知"谁用、为何用、何时用"后，用专业视角**主动指出**可能适用的标配与陷阱，把它们变成可讨论的假设，再让用户取舍。这才是"澄清"而非"记录"或"套模板"。

---

## 二、分析维度

对该需求所属的领域/品类，逐项过一遍。不强求每项都深，但每项都要有结论（"有 / 无 / 不适用"）。

### 1. 核心价值要素
这类东西**本质**要解决什么问题？不可缺的那 1-3 个能力是什么？
> 例：背单词 App 的核心价值是"记住"，所以"间隔重复 / 复习调度"是不可缺的；没有它就只是个生词本。

### 2. 业界标配功能
这类产品/系统，**绝大多数**都有哪些功能模块？用户大概率预期有，但原始需求里没提。
> 例：电商 App 的标配——商品浏览、搜索、购物车、下单、支付、订单状态、售后。漏掉任何一项都不完整。

### 3. 典型用户旅程
一个用户从"第一次接触"到"达成目标"会经过哪些环节？每个环节需要什么功能支撑？
> 例：在线教育——发现课程 → 了解详情 → 开始学习 → 持续学习（进度 / 激励）→ 完成评估 → 复盘。每个环节对应一组功能。

### 4. 业界标杆做法
该领域公认做得好的产品/系统，在关键环节上是怎么处理的？有什么被验证过的实践？
> 例：Spaced Repetition（Anki）、即时反馈闭环（Duolingo）、降低启动阻力（首页"继续学习"大卡片）。

### 5. 常见陷阱与反模式
这类项目**经常踩的坑**是什么？哪些做法已被业界证明效果差？
> 例：学习类 App 在学习页塞社交 / 广告打断心流；结果页没有"下一步"形成死胡同；一次性铺题海而非单题聚焦。

## 三、如何呈现给用户

领域分析不是闷头做完就完，必须把发现**结构化地呈现给用户**，作为澄清的起点。

**关键：节点知识是假设，不是答案。** 加载节点后，对其每条标配 / 标杆 / 陷阱，对照用户的具体产品逐条判"**适用 / 调整 / 不适用（+原因）**"——只呈现过判断的结论，明显不符的直说"此产品不需要，因为…"。**禁止整段照搬节点原文**；每条结论都要连回用户提到的具体细节。**呈现前自检**：有没有整段照搬节点原文？每条结论是否连回用户具体细节？没有就重写。这才是"分析"，否则只是"念清单"。

```
基于这类产品（<领域/品类>）的专业与业界做法，我先梳理几点：

【核心价值】这类东西本质要解决 <X>，不可缺的是 <A / B>。
【业界标配（已适配）】这类通常有 <C / D / E>——对你的产品逐条判：<C 适用 / D 调整成… / E 不适用，因为…>。
【标杆做法】在 <关键环节>，可参考 <做法>；对标产品 / 标准（每条带来源与复核标注）：<标杆A【内置·节点·复核YYYY-MM】/ 标杆B【模型内置知识·未核对】>。
【常见陷阱】这类项目常踩的坑：<陷阱>，要注意避免。

请看这些是否符合你的预期，哪些要做、哪些先不做？
```

> **产品、标准和时效性事实必须带来源标注**（`【内置·节点·复核YYYY-MM】` / `【模型内置知识·未核对】` / `【联网核实·YYYY-MM】`），规则见第六节。

呈现后，把用户的回应作为"补齐需求语义"的输入。

## 四、何时需要联网搜索

稳定的业务原则可优先使用内置节点；以下信息具有时效性，若要作为关键判断依据，必须联网核实，无法联网时应省略或明确标为未核对：

- 产品当前功能、版本、定价、排名、市场地位或近年变化；
- 现行法律法规、平台政策、行业标准版本；
- 市场规模、份额、典型指标等事实数据；
- 领域较新或冷门，模型对标配 / 标杆没有把握；
- 节点的 `知识复核` 距当前超过 12 个月，且产品事实会影响范围决策。

搜索时聚焦当前决策需要的具体事实，不做开放式竞品调研。稳定的方法论、通用业务规则或仅用于启发的历史案例无需默认联网，但不得把它们表述为当前市场事实。

> 来源强度、复核日期和标注格式见第六节。

### 2. 定位 + 回退算法

1. **定大类**：先判断是否明确属于 C 端 / B 端 / 开发者工具。
2. **逐层下钻**：在大类下，沿子类看是否有更具体的节点匹配（看子节点的"匹配信号"）。
3. **取最深的有内置知识的节点**：
   - 命中 ✅节点 → 加载该文件；并按文件顶部"继承"声明，**一并加载祖先文件**，合并使用。
   - 该层是 ⬜占位 / 无匹配 → **回退到最近的 ✅祖先节点**。
4. **跨域 / 未分类兜底**：如果连大类都不匹配，或同时跨越多个大类且无明确主类，加载 `generic/README.md`。不要为了使用知识树而错误归类。
5. **时效检查**：读取节点顶部 `知识复核`；超过 12 个月时，产品现状、法规、排名和定量事实不得直接当作当前事实使用。

> 每个知识文件统一结构：**匹配信号 / 继承要点 / 核心价值 / 业界标配 / 标杆做法 / 常见陷阱 / 专属澄清**。
> 继承维护：更新父类时，同步各子类文件顶部的"继承要点（速览）"。

## 六、标杆兜底与时效：来源、复核日期、事实强度

领域知识树覆盖了常见品类，但不可能穷尽。标杆用于启发需求取舍，不是必须凑齐的清单；没有可靠对标时可以不列产品，优先给出基于用户上下文的业务判断。

### 1. 命中优先级

1. **命中内置节点** → 可使用其中稳定做法，标出节点与该节点的复核日期。
2. **产品事实可能已变化** → 若该事实影响范围决策则联网核实；否则降格为历史案例或不使用。
3. **未命中具体节点 / 使用 generic** → 可用模型知识提出候选标杆，但必须标未核对；不强制凑 2-4 个产品。

### 2. 来源标注（呈现给用户时每条必带）

| 标注 | 含义 | 何时用 |
|---|---|---|
| `【内置·<节点>·复核YYYY-MM】` | 来自预置节点；日期取节点顶部 `知识复核` | 使用节点中的稳定做法时 |
| `【模型内置知识·未核对】` | 大模型凭自身知识给出，未联网核实 | 兜底补充、常规品类 |
| `【联网核实·YYYY-MM】` | web 搜索核实过 | 冷门 / 新品类 / 市场份额等事实数据 |

### 3. 何时升级到联网核实

是否联网由"该信息是否时效敏感且是否影响决策"决定，而不是由品类是否常见决定。涉及当前产品行为、法规、排名、市场数据时按第四节处理。

### 4. 兜底仍要"适配"，不照念

即便走兜底，模型补的产品也遵守"节点知识是假设"：对照用户的具体产品逐条判"适用 / 调整 / 不适用（+原因）"，连回用户提到的具体细节，不整段堆砌产品名。

### 5. 兜底呈现示例

> 【标杆做法】对标拳头产品（来源见每条尾）：
> - **微信 / 小红书**：综合社交 / 社区的历史参照 —— 【内置·content-social·复核2026-07】
> - **Bark / Cute**：垂类（宠物）社交的参照 —— 【模型内置知识·未核对】
> - **<某近一年新品>**：…… —— 【联网核实·2026-07】

## 七、流程示例：对“做一个记账 App”做领域分析（演示定位 + 命中 finance）

> 以下为方法演示，不代表产品当前能力；产品事实如影响真实决策，应按第四节核实。

**定位**：记账 → 大类 **c-end** → 子类 **finance**（命中"记账 / 理财 / 预算"）→ **命中 `finance.md` ✅**，加载 finance + c-end 合并分析。

【核心价值】记账 App 本质是"让用户清楚钱花在哪、并能坚持记"。不可缺：① 快速记账（低摩擦录入）② 收支分类与统计。

【业界标配】（用户大概率没提但需要）：
- 多账户（现金、银行卡、信用）
- 周期性统计（日 / 周 / 月报表）
- 预算与超支提醒
- 数据导出 / 备份
- 分类自定义

【标杆做法】
- 录入极简：可把随手记、MoneyWiz 作为降低记账摩擦的历史案例【内置·finance·复核2026-07】。
- 自动化：账单导入、周期账单自动生成（银行 / 信用卡 App 通行）。
- 可视化：饼图 / 趋势图是标配。

【常见陷阱】
- 录入流程太长 → 用户坚持不下来（记账类最大流失原因）。
- 分类过细 → 维护成本高，用户放弃。
- 没有快速进入 → 结账时场景用不上。

→ 把以上呈现给用户："这些标配（多账户 / 预算 / 统计 / 导出）你需要哪些？录入要做到多快？" 以此驱动澄清。

### 7.2 适配判断演示：对“做一个 K12 少儿编程启蒙 App”做领域分析

**定位**：少儿编程 → c-end → education → **k12**（命中"少儿 / 编程 / 启蒙"）。加载 k12 + education + c-end。

**关键——不是念 k12.md，而是逐条适配**（节点是假设，对照"少儿编程"这个具体产品判）：

| k12.md 的标配 | 判定 | 原因 / 调整 |
|---|---|---|
| 教材版本（人教/北师大）/ 同步校内 | ❌ 不适用 | 编程启蒙无统编教材、非校内学科 |
| 题型 + 拍照搜题 / 批改 | ❌ 不适用 | 编程是项目 / 代码，不是题 |
| 错题本 | 🔄 调整 → 作品集 / 项目复盘 | 代码不是题，但"做过可回看重做"对应 |
| 知识点掌握度 | ✅ 适用（调整为编程概念：循环 / 条件 / 变量） | — |
| 家长端（学情 / 时长管控） | ✅ 强适用 | 少儿 + 护眼 / 屏幕时间 |
| 考前冲刺 / 真题 | ❌ 不适用（考级除外） | 无标准化考试 |

**适配后呈现给用户**（节选）：
- 【核心价值】让少儿在"拖拽创造"中建立编程思维，不是做题。
- 【标配（已适配）】图形化拖拽编辑器、按概念分级（序列 → 循环 → 条件 → 变量）、作品集、家长端；**不要**教材版本 / 校内同步 / 搜题。
- 【标杆】Scratch（图形化 + 社区）、Code.org（关卡课）、编程猫 / 核桃编程（体系课 + 辅导）。
- 【陷阱】太像"做题" → 失去兴趣；只看不练 → 学不会；无作品输出 → 没成就感。
- 【专属澄清】目标年龄（6-9 图形化 / 10+ 文本）？带辅导还是纯自学？效果看"能做出什么项目"还是考级？

> 对比：若**写死套用** k12.md，会硬塞"教材版本 / 校内同步 / 错题本"——对少儿编程大多不成立。逐条适配判断把这些挡掉了，避免返工。
