# 测试平台 / 自动化测试 领域知识

> 树路径：dev-tools > testing
> 继承：`dev-tools`（API / CLI 优先 / 可扩展 / 可观测 / 幂等可复现 / 文档示例均适用）
> 使用前先读父类：[`README.md`](README.md)

## 匹配信号
- 关键词：测试用例 / 自动化测试 / E2E / UI 自动化 / 录制回放 / 用例管理 / 测试报告 / 压测 / 接口测试。
- 场景：回归套件随 CI 跑、UI 流程录制回放、接口契约与压测、测试结果可视化与失败定位。

## 继承要点（速览）
开发者工具通用全适用；本类增量是——**用例可复现（隔离/幂等）+ 选择性执行（增量）+ 失败可定位（trace/录制）**。自动化测试的头号敌人是"不稳定（flaky）"，一切设计围绕降低 flaky。

## 核心价值要素
把"**回归靠人肉**"变成"可复现、可增量、可信"的自动化。不可缺：① 用例隔离与确定性（不依赖执行顺序/共享状态）② 自动等待与稳定选择器（消除时序 flaky）③ 失败可重放（录制/trace/截图）。

## 业界标配功能
- **用例管理与执行**：用例集、套件、标签、过滤；按标签/路径增量选择执行——因为全量回归越跑越慢后会被开发主动绕过，质量门形同虚设。
- **自动等待 / retry 治理**：UI 测试自动等元素可点击而非 sleep；失败用例自动重试并标记 flaky 隔离——因为固定 sleep 是 flaky 之源，flaky 不隔离会让整个套件失去公信力。
- **隔离与幂等**：每用例独立数据/setup-teardown、可重复跑结果一致；并行执行不互相污染。
- **断言与数据驱动**：参数化/数据驱动用例、软断言、契约校验（断言响应结构而非硬编码）。
- **失败可定位**：失败自动截图/录屏/trace（Playwright trace viewer）、DOM 快照、网络日志——因为"红了一条用例但看不出为什么"会直接导致用例被注释掉。
- **报告与可观测**：HTML/Allure 报告、耗时/通过率/历史趋势、flaky 率追踪；报告要能被 CI 消费（机器可读）。
- **录制回放 / 代码生成**：录制操作生成脚本，降低用例编写门槛。
- **能进 CI/CD**：CLI/headless 模式、可并行、产物（报告/截图）可作为 CI artifact；API/CLI 是自动化入口。

## 业界标杆做法
- **Playwright**：现代 E2E 事实标准 — 自动等待 + trace viewer + 跨浏览器 + codegen，做对了"把 flaky 降到极低 + 失败可逐帧回放"。
- **Cypress**：浏览器内运行 + 实时重载 + 截图录屏 — 做对了"开发期调试 DX 最好"，短板是跨 tab/多 origin 历史受限。
- **Selenium**：WebDriver 协议鼻祖 + 跨语言/跨浏览器 — 做对了"标准化协议与生态覆盖最广"，是 W3C WebDriver 规范之源。
- **Appium**：移动端 WebDriver — 一套 API 驱动 iOS/Android，做对了"移动端跨平台与复用 Selenium 心智"。
- **Postman / Newman**：接口测试 + 集合 + CLI(Newman) — 做对了"接口用例即文档、Newman 直接进 CI"。
- **JMeter / k6**：压测 — JMeter 做 GUI 编排老牌、k6 用 JS 脚本化做对了"测试即代码 + 高并发"。
- **TestNG / pytest**：单测/集成框架 — TestNG 做对了依赖与分组并行、pytest 做对了 fixture 与插件生态。

## 常见陷阱与反模式
- flaky 不治理（时序 sleep、共享状态、依赖顺序）→ 偶发红绿让整个套件失去公信力，最终被开发当噪音忽略或注释掉（自动化测试最大死因）。
- UI 测试用脆弱选择器（xpath 绝对路径/易变 class）→ 一改样式就全红，维护成本压垮团队；应优先 role/data-testid 稳定选择器。
- 全量 E2E 跑得很慢且无增量选择 → CI 反馈慢，开发为省时间手动跳过或本地不跑。
- UI 测试当单测用（覆盖过多细粒度断言）→ 又慢又脆；正确是金字塔：单测厚、E2E 薄且只覆盖关键路径。
- 失败只给一行堆栈、无截图/trace/网络日志 → 排障靠猜，用例被频繁注释。
- 测试硬编码环境/数据、不隔离 → 换环境就挂、并行互相污染。

## 本节点专属澄清
- 测试分层是**金字塔**还是倒金字塔（UI E2E 占比）？E2E 只覆盖关键路径吗？
- 选择器策略是否**稳定**（role / data-testid 而非易变 xpath）？
- **flaky 如何治理**（自动等待 / retry 隔离 / flaky 率追踪）？
- 失败产物是否**可回放定位**（trace / 录屏 / 截图 / 网络日志）？
- 要不要**增量选择**（按标签/路径/变更影响面）避免全量回归拖慢 CI？
- 要能进 CI 吗（headless + CLI + 机器可读报告 + 并行）？压测是否纳入（k6/JMeter）？
