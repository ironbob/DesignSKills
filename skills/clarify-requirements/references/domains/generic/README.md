# 跨域 / 未分类 领域知识

> 树路径：generic
> 继承：无（根节点）
> 知识复核：2026-07
> 用途：需求不适合归入 C 端、B 端或开发者工具，或同时跨越多个大类且没有明确主类时使用。

## 匹配信号
- 涉及硬件、公共服务、科研、内容生产、现场作业、基础设施或多类系统组合。
- 现有领域树没有合适根节点；强行归类会引入错误标配。

## 核心价值要素
先建立不依赖品类的需求骨架：① 目标结果与成功证据 ② 参与角色与责任边界 ③ 关键业务对象、规则和生命周期 ④ 风险、依赖与明确范围。

## 业界标配功能
- 不预设登录、消息、排行榜、审批等所谓通用功能；只有能直接支撑目标场景时才纳入。
- 用“触发 → 业务行为 → 结果 / 异常”检查主闭环。
- 明确角色权限、跨角色交接、数据或实物的责任归属。
- 检查安全、隐私、合规、无障碍、现场环境和人工兜底中哪些适用。
- 对跨系统能力明确外部依赖、失败传播和责任方。

## 业界标杆做法
- **ISO 9241-210**：以用户、任务和使用环境为中心理解需求；具体版本与条款如影响决策需联网核实。
- **GOV.UK Service Manual**：从端到端服务和多角色协作审视需求；当前内容如作为依据需联网核实。

## 常见陷阱与反模式
- 为了命中知识树强行归类 → 把不适用的注册、留存、审批或开发者能力当作标配。
- 先列功能再定义目标与角色 → 功能很多但没有可验证的业务闭环。
- 只写成功路径 → 交接失败、无权限、状态冲突或外部依赖失败时无人负责。
- 把跨域复杂性都记成“技术问题” → 业务责任、规则和异常结果没有被需求定义。
- 用不相关头部产品凑标杆 → 形成竞品锚定，掩盖真实领域知识缺口。
