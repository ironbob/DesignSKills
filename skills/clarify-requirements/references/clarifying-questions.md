# 澄清问题与边界控制

> 配合 clarify-requirements skill 的模式选择、获取上下文与补齐需求语义步骤使用。
> 核心纪律：**先建议 Lite / Full、由用户决定；遵守所选问题额度；多选优先；描述业务行为，不设计实现。**
> 本 skill 独立，只负责需求澄清，不涉及设计 / 技术实现。

## 零、推荐模式，由用户决定

在提出实质性澄清问题前，根据现有请求给出建议：

| 模式 | 问题额度 | 推荐条件 | 完成标准 |
|---|---:|---|---|
| **Lite** | 最多 6 个问题、2 轮，每轮 1-3 个 | 单一用户、单一主流程、低到中风险、想快速验证或用户希望少问 | 只解决最高影响歧义，其余写成假设、风险或未决问题 |
| **Full** | 通常 6-12 个问题，每轮 1-3 个 | 多角色、多流程、上线改造、外部依赖或高风险领域 | 目标、角色、规则、状态、异常、约束、验收和范围无实质歧义 |

推荐 Full 不等于替用户决定。展示建议、理由和两种模式，让用户选择后再开始提问。用户已指定 Lite / Full 时直接采用；用户说"按建议"时采用推荐模式；用户可随时切换。

问题按**独立决策主题**计数。例如"谁使用、何时使用、成功指标是什么？"应计 3 个，不能包装成 1 个问题。Full 已足够清晰可少于 6 个；预计超过 12 个时先解释剩余风险，并请用户决定继续 Full、切 Lite 或先产出阶段性文档。

推荐规则：

- 命中交易、资金、医疗、未成年人、隐私、企业权限等高风险因素时，建议 Full。
- 存在两个及以上角色、关键状态流转、跨系统依赖或多条主流程时，建议 Full。
- 只有一个主用户与主闭环，且目标是快速验证、需求失败可低成本回滚时，建议 Lite。
- 信息不足以可靠判断时，说明不确定性并建议 Full；仍由用户决定。

用户逆建议选择时：

- 建议 Full、用户选 Lite：尊重选择，在文档中列出未深挖风险与未验证假设。
- 建议 Lite、用户选 Full：按 Full 系统澄清，不劝用户降级。

## 一、先获取最小上下文

领域分析前至少知道以下信息：

- 谁是主要用户或决策角色；
- 要改善什么结果；
- 最主要的使用场景；
- 当前是验证想法、首版上线，还是改造既有能力；
- 已知的一个最硬约束（如有）。

Lite 从这些信息中选择影响最大的最多 6 项，在最多 2 轮内完成；Full 按需补齐。问题需要用户长篇思考、前一个答案会改变后一个问题、或涉及高风险取舍时，拆开问。

## 二、澄清问题分类

按以下类别组织提问。Lite 只取最高影响项，Full 系统覆盖适用项；已有答案就跳过，不为覆盖清单或达到数量下限而重复问。

### 1. 目的类（最先问）
- 这个东西最终解决什么问题？没有它会怎样？
- 如果只能留一个最核心的能力，是哪个？
- 做完之后，怎么判断它"成了"？

### 2. 用户类
- 主要给谁用？他们现在怎么解决这个问题？
- 还有没有第二类用户？谁**不是**目标用户？

### 3. 场景类
- 用户在什么情境下会用？（时间 / 地点 / 设备 / 前后动作）
- 第一次用和熟练之后，用法一样吗？
- 多久用一次？一次用多久？

### 4. 角色、业务对象与规则类
- 谁可以创建、查看、修改、审批或关闭？哪些角色明确不能做？
- 业务里有哪些关键对象？它们分别代表什么，不要细化成字段或表。
- 对象会经历哪些业务状态？什么事件允许它进入下一状态？
- 哪些规则必须始终成立？有哪些例外或人工兜底？

### 5. 约束类
- 有没有平台 / 时间 / 预算 / 合规上的硬限制？
- 有没有必须兼容的现有系统或数据？
- 有没有不能碰的红线（绝对不做某事）？

### 6. 领域强制关注类

不要等待用户主动提及。根据领域主动提示与需求有关的安全、隐私、合规、无障碍和数据治理风险，让用户选择：

- **确认纳入**：写成业务或非功能约束；
- **明确排除**：写明原因和风险承担；
- **暂未决**：写明影响与决策责任方。

只确认要求，不设计加密、存储、鉴权或合规技术方案。

### 7. 成功标准类
- 上线后看哪个指标判断有效？（要可量化的）
- 什么程度算"够用"，可以停手？
- 有没有不能接受的失败情形？

### 8. 范围边界类（最后问）
- 哪些是你想过但决定先不做的？
- 有没有看起来相关、但其实不该塞进来的？
- 本期 MVP 最少要有什么，你才会真的用它？

## 三、好问题 vs 坏问题对照

| ❌ 坏问题（含糊 / 开放式过载） | ✅ 好问题（具体 / 聚焦 / 易答） |
|---|---|
| 你要什么功能？ | 这个 App 主要给谁用、什么场景下打开它？ |
| 需求都清楚了吗？ | "做完后用哪个指标判断它成了"——你能定一个吗？ |
| 有什么特殊要求？ | 有没有平台限制：只要手机，还是也要网页？ |
| 功能要多少？ | 本期 MVP 最少要有什么，你才会真的用它？ |
| 你觉得还需要什么？ | 我列了 A/B/C 三个先不做，你看哪个其实要做？ |

## 四、越界拉回话术

当用户（或自己的思路）滑向交互 / UI / 技术层时，用以下话术拉回，并记入"未决问题"。**不在本阶段展开这些话题。** 本 skill 只负责需求澄清，不涉及设计 / 技术实现。

### 交互类（页面 / 按钮 / 跳转 / 布局）
> "『首页怎么布局 / 按钮放哪 / 几个 Tab』是交互层的事，超出需求澄清的范围。我们只定『要哪些功能』。先记一笔到未决问题，留给后续的交互设计环节。"

### 技术类（架构 / 技术栈 / 数据模型 / API）
> "『用什么框架 / 数据库怎么设计 / 前后端怎么分』是技术方案的事，超出范围。这阶段只定功能。先记一笔到未决问题，留给后续的技术方案环节。"

### 业务语义不是越界

角色权限、业务对象含义、业务规则、状态变化、成功路径和异常结果属于功能需求，必须澄清。例如可以问"退款申请有哪些业务状态、谁能批准"，但不问"用什么状态机框架、表里有哪些字段"。

### 视觉类（配色 / 字体 / 组件 / 动效）
> "视觉风格是设计环节的事，现在定太早。我们先把功能边界画清楚。"

### 通用拉回句式
- "这个问题很好，但它属于 [交互 / 技术 / 视觉] 决策，不在需求澄清的范围。"
- "我先记到未决问题。本 skill 到产出功能需求文档即结束，不涉及设计 / 技术实现。"

## 五、范围方案切分模板

当存在真实范围取舍时，提出 2-3 档方案，**先说推荐项及理由**。如果只有一个合理范围，直接给出该范围及理由，不为了满足格式虚构档位。

### 切分维度（按优先级 P0/P1/P2 归档）
- **MVP（最小可用）**：只含 P0。判据："没有这个，用户根本不会用它"。
- **标准版（首批上线）**：P0 + P1。判据："核心闭环完整，且 P1 里某项直接决定关键体验指标"。
- **完整版（后续迭代）**：P0 + P1 + P2。判据："没有也行，有了更好"。

### 呈现格式
```
建议三档范围：
- 【推荐】标准版（P0 + P1）：含 xxx 功能。
  理由：核心闭环完整，且 P1 里 <某项> 直接决定 <体验指标>，缺了用户会流失。
- MVP（仅 P0）：含 xxx。适合想最快验证想法 / 资源极度有限。
- 完整版（+ P2）：额外 xxx。适合确定要长期投入。
```

### 切分时的判断要点
- 默认推荐"标准版"，除非用户明确要快速验证（推 MVP）或明确要全量（推完整版）。
- 主动建议砍 P2（YAGNI）——明确告诉用户"这几个我觉得可以先不做"。
- 不替用户决定 P0/P1 边界，但可以质疑："你把 X 放 P0，但在 <场景> 下它似乎不是必需，降到 P1 行吗？"

## 六、确认节奏

- **Lite**：最多 6 个澄清问题、2 轮后停止；每轮 1-3 个。随后集中呈现范围、假设、风险和未决问题，完成一次最终确认。
- **Full**：通常确认范围方案和最终文档两次；多角色、多子系统或高风险需求可按业务模块分段确认，但每段必须对应独立风险或取舍。
- **切换模式**：Lite 切 Full 时从未覆盖类别继续，不重复已答问题；Full 切 Lite 时停止新增问题，把剩余缺口写入假设、风险或未决问题。
