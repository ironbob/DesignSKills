# 明确需求：把模糊想法变成清晰的功能需求

## 目的

把一句模糊的想法，变成一份清晰的**功能需求**。回答：**谁在什么场景下，需要系统表现出什么业务行为，怎样算完成**。不回答交互布局、UI 视觉、技术架构、技术数据模型或 API 设计。

两个核心特征：

1. **独立** —— 只回答业务层的"做什么"，不涉及交互布局、UI 视觉或技术实现。产出需求文档即完成。
2. **专业驱动** —— 先获取最小必要上下文，再用领域知识与业界做法补盲区、纠偏差，避免在不了解用户和场景时套用标配。

```
模糊想法 ──► [clarify-requirements] ──► 清晰功能需求文档（独立产出）
```

## 先判断适用性，再选择提问模式

请求已经具体、低风险且验收清楚时，例如明确的工具函数、局部配置或样式修改，说明需求足够清晰并结束本 skill，不强制生成 PRD。

需要澄清时，先根据现有信息给出模式建议与理由，再由用户决定最终模式：

- **Lite**：最多 **6 个澄清问题、2 轮**，每轮 1-3 个，只追问最影响目标、范围和验收的决策。适合单一用户、单一主流程、低到中风险、快速验证或用户明确希望少问。未覆盖的信息必须作为假设、风险或未决问题写入产物，不能默认为已确认。
- **Full**：通常 **6-12 个澄清问题**，每轮 1-3 个紧密相关问题，覆盖目标、角色、场景、业务对象、规则、状态、异常、约束、成功标准和范围。适合多角色、多流程、上线改造、外部依赖，或交易、资金、医疗、未成年人、隐私、企业权限等高风险需求。

问题数量按一个独立决策主题计数，禁止把多个不相关问题塞进一个长句规避额度。Full 不为凑数硬问；实质歧义已消除可提前结束，预计超过 12 个时先说明原因并征得用户同意。

使用以下格式让用户选择：

> **建议模式：Full / Lite** —— <结合当前需求说明理由>
>
> - Lite：最多 6 个关键问题、2 轮，更快，但会保留更多假设
> - Full：通常 6-12 个问题，更系统
>
> 请你决定最终使用 Lite 还是 Full。

用户的选择高于建议：用户已指定模式时直接采用；用户说"按你的建议"时采用推荐模式；用户可在澄清过程中随时切换。即使推荐 Full 而用户选择 Lite，也必须尊重选择，并显式记录未深挖的风险。

<HARD-GATE>
用户选择模式后，在该模式的需求产物被确认前，不进入实现、设计或技术方案动作。本 skill 到需求确认即结束，不自动调用下游实现或设计 skill。
</HARD-GATE>

## 边界（最重要）

**产出**（功能层）：
- 一句话目标
- 目标用户与核心场景（谁用、解决什么、何时用）
- 角色与权限边界
- 业务对象与术语（只定义业务含义，不设计表、字段或类）
- 业务规则、状态与生命周期、主成功路径和关键异常
- 功能清单（分组 + 优先级 P0/P1/P2 + 每功能简述）
- 每个核心功能 1-3 条可验收标准
- 明确不做（Out of scope）
- 用户主动提及的非功能约束，以及领域强制关注项的取舍结论
- 外部依赖与未决问题

**不产出**（超出本 skill 范围，记入"未决问题"即可）：
- ❌ 交互实现：页面、按钮、跳转、布局、动效
- ❌ 技术方案：架构、技术数据模型、技术栈、API 设计
- ❌ UI 视觉：配色、字体、组件、动效

允许描述实现无关的业务语义，例如"订单由待支付变为已支付"、"管理员可以关闭工单"、"退款超过 7 天不可发起"；禁止把这些下钻成数据库表、接口字段或页面操作。

**越界拉回**：当对话滑向"页面怎么布局""用什么框架""按钮放哪"时，明确说"这超出需求澄清的范围，先定清楚要哪些功能"，记一笔到"未决问题"，不在本阶段展开。完整话术见 `references/clarifying-questions.md`。

## Checklist

复杂任务可使用计划工具跟踪进度，但不要机械地为每一步创建 task。

1. **判断适用性** —— 已足够清晰则结束本 skill；需要澄清则继续。
2. **推荐并确认模式** —— 基于歧义、角色 / 流程复杂度、产品阶段、依赖和风险推荐 Lite 或 Full；展示两种模式后等待用户最终选择。用户已指定或授权采用建议时不重复询问。
3. **按模式获取上下文** —— 用一句话复述需求，按所选额度提问。Lite 最多 6 个问题、2 轮，每轮 1-3 个，优先目标、主用户 / 场景、范围 / 验收；Full 通常 6-12 个问题，每轮 1-3 个，系统补齐需求语义。已有答案不重复问。
4. **领域分析（专业 + 业界做法）** —— 基于已确认的上下文定位最匹配节点；若三大类均不匹配，使用 `generic` 节点，不强行归类。将节点内容逐条判断为"适用 / 调整 / 不适用（+原因）"，只呈现与当前需求有关的结论。标杆与事实的时效规则见 `references/domain-analysis.md`。
5. **补齐或记录缺口** —— Full 围绕目的、角色、业务对象、规则、状态、异常、约束、成功标准和范围边界消除实质歧义；Lite 到达额度后停止提问，把未确认内容标成假设、风险或未决问题。详见 `references/clarifying-questions.md`。
6. **提出范围方案** —— 只有存在真实取舍时才给 2-3 个方案（如 MVP / 标准 / 完整），说明权衡并推荐；若只有一个合理范围，直接说明理由，不虚构方案。
7. **确认范围** —— 把推荐范围、关键取舍和明确不做集中呈现，获得一次确认。高风险或多角色系统可按业务模块分段确认；普通需求不要逐段反复确认。
8. **写功能需求文档** —— 存到 `prd/`（或用户指定目录），文件名 `YYYY-MM-DD-<主题>-requirements.md`，使用 `references/requirements-template.md`。文档必须记录模式建议、用户最终选择；Lite 还需列出未验证假设。
9. **自审** —— 检查模式与问题额度、消歧、placeholder、scope、业务规则、状态异常、约束、验收、out-of-scope 和领域盲区，发现问题就地修。
10. **最终确认** —— 请用户 review 完整文档；修改后重跑受影响检查。用户确认即结束。

## 自审检查项

写完文档后用新视角过一遍：

1. **Placeholder 扫描** —— 正文功能不能含 placeholder（如 "TBD/TODO/待定/之后再说/适当处理"）；真实未决问题必须写成"问题 + 影响 + 后续决策阶段"。
2. **模式一致性** —— 是否记录建议、理由和用户最终选择？Lite 是否最多问 6 个问题、最多 2 轮并标出未验证假设？Full 是否系统覆盖但没有为凑数量硬问？
3. **消歧** —— 任何功能能否被理解成两种意思？Full 应继续澄清；Lite 应选择一种有依据的写法并标为假设。
4. **业务语义** —— 角色权限、业务对象、规则、状态变化和关键异常是否足以解释系统应有行为？
5. **Scope 检查** —— 是否聚焦到单一可实施范围？多个独立子系统需拆分。
6. **Out-of-scope 明确** —— "明确不做"是否列了？是否够狠（YAGNI）？
7. **约束复查** —— 用户约束与该领域必须关注的安全、隐私、合规、无障碍等是否已确认、排除或记为未决？
8. **验收可证** —— 每条验收标准能不能被客观判定通过/不通过？不能就改写。
9. **领域盲区复查** —— 领域分析指出的标配功能，是否都已明确"做"、"不做"或"Lite 未深挖"？

发现问题就地修，不必重审。

## 产出文档

存到 `prd/`（或用户指定目录），文件名 `YYYY-MM-DD-<主题>-requirements.md`，使用 `references/requirements-template.md` 的结构。日期用当天。

## 关键原则

- **先有上下文，再专业分析** —— 先知道谁用、为何用、何时用，再用领域知识补盲区；不盲目接受初始想法，也不盲目套用竞品。
- **用户决定模式** —— 主动推荐 Lite / Full 并解释理由，但最终模式由用户决定，且可中途切换。
- **遵守问题额度** —— Lite 最多 6 个、2 轮，每轮 1-3 个；Full 通常 6-12 个、每轮 1-3 个。不要拆句规避额度，也不要为凑数量硬问。
- **多选优先** —— 比开放式更易答。
- **YAGNI** —— 狠心砍掉可做可不做的功能；推方案时主动建议精简。
- **描述业务行为，不设计实现** —— 可以写角色、规则、状态和异常；不写页面、数据库、API 或技术栈。
- **关键节点确认** —— 普通需求只强制确认范围和最终文档；复杂高风险需求才分段确认。
- **可回头** —— 任何时候觉得不对，回去澄清。

## 反模式

| 反模式 | 正确做法 |
|--------|----------|
| 还不知道谁用、为何用就先套竞品 | 先获取最小上下文，再做适配后的领域分析 |
| 越界到页面/按钮/布局 | 拉回，记入未决问题 |
| 越界到架构/技术栈 | 拉回，超出范围 |
| 一次抛出大量不相关问题 | 一次问 1-3 个紧密相关问题；高负担问题拆开 |
| 根据风险直接替用户选择 Full | 给建议和理由，展示 Lite / Full 后让用户最终决定 |
| Lite 超过 6 个问题、2 轮，或把多问藏进一句 | 遵守 6 个独立决策主题、2 轮的总额度，缺口记为假设 / 风险 |
| Full 为达到 6 个问题重复提问 | 已有答案不再问，实质歧义消除即可提前结束 |
| 每个小节都要求用户确认 | 普通需求只确认范围和最终文档 |
| 功能含糊："支持课程管理" | 具体到："创建/编辑/删除/归档课程" |
| 只有功能名，没有角色、规则和异常 | 补齐业务行为，但不下钻到技术实现 |
| 没有明确 out-of-scope | 必须列出"明确不做" |
| 跳过场景直接列功能 | 先锁定谁用、何时用 |
| 验收写成"体验要好" | 写成可判定："评分延迟 < 2 秒" |
| 假设并调用某个下游 skill | 本 skill 独立，结束即终止 |
