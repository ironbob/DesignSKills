# 范围界定与机制类型识别（模块 A）

> 配合 `tech-mechanism-analysis` 的 Checklist 第 1/2 步使用。本 skill 的分析对象是**单个技术机制**，范围界定 + 类型识别决定了后续套哪套链路模板、追哪些调用链。范围未确认前不深挖（HARD-GATE）。

## 一、机制对象界定

用户给的是「一个技术机制 / 技术点」，不是「一个业务」也不是「整体架构」。常见输入形态：

- **名称 + 入口提示**：如「关键帧实现，入口在 `Timeline::addKeyframe`」「图片缓存的 LRU，看 `ImageCache`」。
- **根路径**：可跨多目录（机制常散落在 store / runtime / render 等多处）。

界定时要做：

1. **从入口提示定位候选代码地图**：关键文件 + 入口 `file:line` + 一句话职责。
2. **枚举覆盖文件集合**（`rg --files` / `find`），剔除 build/test 产物（除非用户明确含）。
3. **识别多语言技术栈**（按后缀 + 内容），标注各语言结构 / 依赖分析精度。

> 最大风险：**圈错机制 / 拉入无关代码或漏关键调用链**。机制是纵向贯穿的——存储、读取、处理、生效可能各在一处，别只圈入口文件。

## 二、机制类型识别（决定套哪套链路模板）

读完候选代码后，判该机制属于哪类，记录依据。详见 `mechanism-type-templates.md`，速查：

| 类型 | 匹配信号 | 链路模板 |
|------|----------|----------|
| `data-flow` 数据流型 | 有数据被产生 → 存储 → 读取 → 变换 → 作用于输出（关键帧、缓存、管线） | 产生→流转→处理→生效 |
| `lifecycle` 生命周期型 | 有 init/configure/run/teardown 的状态推进（资源管理、会话） | 初始化→配置→运行→清理 |
| `call-chain` 调用链型 | 一次操作沿 入口→委派→核心→副作用 传递（请求处理、命令分发） | 入口→委派→核心→副作用 |
| `state-machine` 状态机型 | 有显式状态 + 转移 + 动作（播放器状态、协议状态机） | 状态→转移→动作 |
| `other` | 以上都不贴 | 自定义分段（须说明） |

**类型是假设**：对照具体机制判适用 / 调整，给依据；拿不准时回退 `data-flow`（最通用）或 `other` 并在 `mechanism_type_basis` 写明，不硬塞。

## 三、多语言精度标注

- 有规范模块 / 类型系统的语言（JVM、Go、TS）：结构 / 依赖精度 **high**。
- 靠目录约定 / import 启发的语言（Python、C++ 依赖靠 `#include`/命名空间）：精度 **medium**/`low`，结论更保守，登记缺口。
- 每种语言在 `language_precision[]` 里独立标注 `{language, precision, note}`。

## 四、两段式确认（HARD-GATE）

把以下内容**呈现给用户确认**，未确认不进下一步：

- **机制对象**（名称 + 入口提示）
- **机制类型 + 判定依据**（如「数据流型：关键帧被产生并存入时间线、播放时读取、插值处理、作用到渲染属性」）
- **套用的链路模板**（如 `produce→flow→process→effect`）
- **覆盖文件集合**（N 个文件 / 涉及哪些目录）
- **多语言技术栈 + 各语言精度**
- **一句话机制职责**

确认话术示例：

> 「机制对象：关键帧缓动；类型判为 **数据流型**（依据：关键帧被创建并存入时间线 → 播放时按时间查找 → 缓动插值 → 写入渲染属性），套模板 `产生→流转→处理→生效`；覆盖 3 个文件；语言 TypeScript（精度 high）。职责：在时间线上对属性做带缓动的关键帧插值。这个范围和类型对吗？」

**未确认不深挖、不分段、不产出。** 用户修订后回到本步重确认。
