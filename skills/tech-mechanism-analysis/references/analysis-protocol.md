# 代码读取与取证协议

## 沿真实链路追踪

每阶段回答：

1. 数据或控制从哪里进入？
2. 本阶段改变了什么？
3. 交给下一阶段时是什么形态？
4. 最终由谁观察到效果？

记录五类事实：数据/状态、调用/依赖、算法/变换、时序/并发、边界/兜底。

链路可能分支、合流、循环或异步。不要为了套模板删掉这些关系。

## 工具降级

优先使用当前环境已有的最高质量证据：

1. LSP、类型检查器、编译器或静态分析；
2. 代码搜索和 import/include 追踪；
3. 测试、最小运行或等价求值；
4. 文档和注释仅作线索，不单独作为实现结论。

某工具不可用时自动降级，不例行等待安装。把缺失的调用边或运行验证反映到 `language_analysis[].confidence` 和 `gaps`。

## 证据纪律

- 每条 `evidence` 必须有真实文件、有效行号和说明该位置支持什么的 `note`。
- 实现事实与跨段交接分别记录 `evidence` 和 `handoff_evidence`，不要用一条笼统证据代替交接契约依据。
- 使用 repo-root 相对路径；不使用绝对路径、`..` 或指向 repo 外部的符号链接。
- 证据行附近出现一个同名标识符只能证明位置相关，不能自动证明整条结论。
- 设计意图不能从代码结构直接推出；无直接证据时使用 `why_basis: inferred` 或 `unknown`。
- 注释与实现冲突时以实现和运行行为为准，并记录冲突。

校验脚本只能检查路径、行号和有限的标识符近邻，不能证明“该行语义上支持该结论”。交付前逐条人工复核证据语义。

## 数值操作识别

插值、滤波、归一化、变换、量化、聚合、哈希分布、时间计算和影响行为的索引运算属于候选数值操作。

- Lite：只展开理解机制必需的核心运算。
- Full：每个标记为 `numerical=true` 的阶段至少一个工作示例。

## 聚焦

先读入口、核心处理和最终效果，再补存储、适配器和边界。只追与目标机制有关的调用链；不要把全仓库巡检伪装成机制分析。
