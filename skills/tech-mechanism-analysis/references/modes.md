# Lite / Full 模式

## 选择规则

| 场景 | 模式 |
|---|---|
| 快速理解、接手代码、解释一个技术点、时间有限 | `lite` |
| 深度分析、正式交接、可审计报告、设计债审计、JSON 契约 | `full` |
| 用户未指定 | `lite` |
| 用户明确指定 | 服从用户 |

开始时用一句话声明模式。不要为了选择模式额外询问用户。

## Lite

目标是以较低成本形成正确的心智模型。

- 候选范围可以边追踪边修订，不设置例行确认门。
- 产物默认为一份 Markdown；用户明确只要聊天回答时不落盘。
- 链路通常为 3–6 段，可包含分支、循环或异步衔接。
- 在全链路正文前强制输出业务流程图、时序图和架构角色图，并通过结构与证据校验。
- 数值示例只覆盖理解机制所必需的核心运算。
- 设计观察最多 3 条，优先与用户目标或已知演进方向有关。
- 只运行 `validate_report.py`。

Lite 不是草率模式：关键事实仍须证据可达，推断仍须标记。

## Full

目标是形成可复核、可交接、可机器检查的机制档案。

- 先确认候选范围并写入 `scope_confirmations`；追踪中发生实质扩围时再次确认并追加记录。
- 每个数值阶段都必须有忠实工作示例。
- `analysis.json` 必须包含三张独立的必检图；每张图的节点、边和架构职责均可追溯。
- 设计债覆盖架构、逻辑和跨阶段衔接，但允许某一轴为空。
- `analysis.json` 是唯一事实源。
- `analysis.md` 必须由 `render_report.py` 生成，不手写。
- 先人工复核证据语义，再运行 JSON、证据位置、报告结构和确定性契约校验。

## 模式切换

- `lite → full`：保留已有取证，补范围确认、完整数值覆盖、设计债字段和 JSON 契约。
- `full → lite`：停止扩展正式契约，提炼已确认事实为 Lite 报告；不得把尚未确认的 Full 推断当事实。

模式切换不需要重做已经验证过的代码读取。
