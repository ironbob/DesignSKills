# 评分档位 + 整体档位 + 亮点/风险（模块 C）

> 配合 `arch-overview` 的 Checklist 第 6、7 步使用。这一步把 4 维评估「定档、汇总、点亮点与风险」，是「架构总览」的核心输出（PRD §4-C）。**所有判定都要可解释、可回链**，不是主观打分。
>
> **与 `arch-quality-eval` 的关键区别**：那里是 critical/major/minor 坏味道分级 + go/no-go 重构决策 + P1/P2/P3 重构优先级；**这里是 优/良/中/差 正向设计档位 + 整体优秀度 + 亮点/前瞻性风险**。不分级、不下 go/no-go、不给重构优先级。

## 一、分维度档位：优 / 良 / 中 / 差

档位看「**该维度设计相对业界成熟做法的健康度**」，不看代码行数、不抄 lint 阈值。先问：「这一维设计符合业界成熟做法吗？差距多大？影响可演进性吗？」

| 档位 | 判定标准（客观、可解释） | 典型表现 |
|------|------------------------|----------|
| **优** | **符合或接近业界成熟做法**，无明显差距，结构清晰、易于理解与演进 | 分层纯净单向、职责单一边界清晰、扩展点恰到好处、命名表意自解释 |
| **良** | **基本符合**，有小差距但不影响整体健康，局部可优化 | 主体良好，个别处偏离（如个别跨层、个别命名不表意），但不构成系统性问题 |
| **中** | **存在明显差距**，部分不符合业界做法，演进/理解有一定阻力 | 多处反向依赖、部分模块职责混杂、扩展需改既有代码；但尚可维护 |
| **差** | **严重偏离业界做法**，结构混乱或难以演进，是该维度的系统性问题 | 系统性循环依赖、上帝类遍布、变化散落严重、结构无法一眼看懂 |

### 分档自检（每维必答）

1. **与业界做法的差距** —— 现状偏离业界成熟做法多少？偏离是局部（良/中）还是系统性（差）？符合度高（优）？
2. **影响面** —— 偏离影响单个模块，还是跨模块/整个 app？跨模块→ 至少中。
3. **可演进性** —— 这个维度的现状会不会阻塞未来演进/扩展？阻塞 → 中/差。
4. **证据强度** —— 有 file:line / 图节点实锤 → 正常定档；仅推断 → 标 `⚠ 未确认` 并在档位表述加「疑似」，不得直接定差。
5. **多语言精度** —— 低精度语言上的判断要保守，无法实锤的差距降一档表述 + 登记缺口。

> 边界情形：**「差」要克制**——只有系统性、严重偏离业界做法、明显阻碍演进的结构才给差。宁可写「疑似差 ⚠ 待确认」，也不凭印象判差。「优」也要克制——普遍良好无重大差距才给优，多数健康系统应在 良/中。

## 二、整体档位：汇总规则（可解释，非简单平均）

整体档位由 4 维汇总，**不是简单算术平均**。规则（按优先级）：

1. **地基维度优先**：`layering`（分层&依赖）和 `cohesion`（职责内聚&边界）是架构地基。若两者之一为「差」，整体通常不高于「中」（地基溃烂拖累整体）。
2. **短板效应**：任一维度为「差」→ 整体不超过「中」（除非该「差」是单一局部、有证据证明不影响整体——需在报告里说明）。
3. **多数原则**：无「差」时，整体取多数维度的档位；2 维优 + 2 维良 → 整体「良」（偏高）。
4. **可演进性加权**：若 `extensibility`（可扩展性）为「差」且证据显示阻塞演进，整体下调一档。

汇总表（给方向，非机械公式）：

| 整体档位 | 典型 4 维组合 | 含义 |
|----------|--------------|------|
| **优** | 无中/差，至少 2 维优 | 整体设计健康，符合业界做法，易理解易演进 |
| **良** | 无差，最多 1 维中 | 整体良好，局部可优化，不影响大局 |
| **中** | 有中但无系统性差，或地基维度中之一为中 | 整体可用但有明显差距，演进有阻力 |
| **差** | 地基维度差，或系统性差 | 整体设计偏离业界做法，难以理解与演进 |

> **整体档位必须在报告中给出汇总依据**（哪几维是什么档、为什么汇成这个整体），让读者能复现判定。`validate_overview.py` 不强制算法（无法机械校验主观汇总），但 `validate_report.py` 检查报告是否含整体档位 + 维度档位陈述。

## 三、亮点（Highlights）—— 设计得当、值得保持

从正向视角找出**做得好的设计选择**——这些是架构的资产，明确点出让团队知道「这部分保持住」。

- **是什么**：符合/接近业界成熟做法、解决得好、值得保持的设计选择（如：清晰的分层、到位的抽象、合理的边界、表意的命名、恰到好处的扩展点）。
- **每条字段**：`id`（`HL-NN`）+ `title` + `dimension`（指向哪维）+ 一句为什么是亮点 + `evidence`（回链 file:line / 图节点）。
- **纪律**：亮点必须挂证据（确实是设计得当的事实，不是拍马屁）；低质量报告不应硬凑亮点，无亮点时 `highlights: []` 允许（但通常一个真实系统总有做得对的地方）。

## 四、风险点（Risks）—— 总览级、前瞻性（不分级、不下 go-no-go）

从**正向设计视角**前瞻性地点出「**这个选择在未来可能演进成问题**」——这是总览级别的方向性提示，**不是坏味道逐条诊断**。

- **是什么**：当前可能还行、但从设计健康度看，未来某场景下可能成为隐患的选择（如：某处扩展需改既有代码、某边界略模糊可能在业务增长后耦合、某隐式依赖在重构时会暴露）。
- **每条字段**：`id`（`RISK-NN`）+ `title` + `dimension`（指向哪维）+ `note`（前瞻性描述：未来什么场景下可能怎样）+ `evidence`（回链 file:line / 图节点）。
- **关键纪律（与 arch-quality-eval 划界）**：
  - ❌ **不分级** critical/major/minor（那是坏味道诊断）。
  - ❌ **不下 go/no-go**（那是重构决策信号）。
  - ❌ **不给重构优先级 P1/P2/P3、不给重构方案**（那是 `arch-quality-eval` / 重构阶段）。
  - ✅ 只做**总览级、前瞻性、描述性**提示：「这个选择在 X 场景下可能 Y」，指方向不写方案。
- **数量克制**：风险点抓**结构性、前瞻性**的少数关键，不刷一堆细枝末节（噪音淹没总览）。

> 若用户想对某个风险点深挖「到底多严重、要不要重构」——明确说「这超出架构总览范围」，指向 `arch-quality-eval` 做坏味道诊断。

## 五、自审清单（Checklist 第 7 步用）

逐维度 + 整体 + 亮点/风险过：

1. **档位可解释** —— 每维档位能用「与业界做法差距 + 影响面 + 可演进性 + 证据强度」说清，不是「感觉像优」。
2. **整体可复现** —— 整体档位给了汇总依据（哪几维什么档、为什么汇成整体），读者能复现。
3. **业界对照 provenance** —— 每维业界做法声明 LLM内置经验 + 未核对 + 延伸阅读，无假装权威。
4. **亮点挂证据** —— 每条亮点回链事实，不是空泛称赞。
5. **风险点不越界** —— 风险点是前瞻性描述，未分级、未下 go/no-go、未给重构方案/优先级。
6. **多语言精度诚实** —— 低精度语言结论保守 + 登记缺口。
7. **未确认隔离** —— `⚠ 未确认` 的项在「已知缺口」有对应登记。

## 六、建议性 LLM 裁判（不阻断，非门禁）

> 对标 `arch-quality-eval` 的 severity-and-priority §五：确定性脚本门（退出码）是唯一硬卡；这一节是**建议性**复核，**从不影响退出码**，用于 catch 脚本判不出的「档位失真 / 整体汇总不当」。

档位写完后，用下面提示词做一次建议性复核（可由人，也可由 LLM），据发现修：

```
你是架构评审裁判。下面是一份「架构总览」的 4 维档位 + 整体档位 + 亮点/风险。
请只做建议性复核，不改变事实，只指出【档位失真】与【整体汇总不当】两类问题：

1. 档位失真：有没有某维档位给得过松（其实差距明显该降档）/ 过紧（其实只是疑似待确认）？
   逐维对照判定标准：优=符合业界做法无明显差距；良=基本符合小差距；中=明显差距有阻力；差=系统性偏离难演进。
2. 整体汇总不当：整体档位是否与各维度档位可解释地一致？地基维度(layering/cohesion)为差时整体是否仍过高？
   有无短板被忽略（某维差但整体没体现）？

输出：逐项只在你认为有问题时点名（维度/整体 + 问题 + 建议档），没问题的不输出。
不得编造证据，不得新增维度，不得把风险点改成分级坏味道或下 go/no-go。
```

裁判结果**不进退出码**；采纳与否由分析者在自审时决定，改完重跑四道门。
