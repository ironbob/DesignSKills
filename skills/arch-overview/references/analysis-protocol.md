# 代码读取取证协议（模块 B/C 的证据来源）

> 配合 `arch-overview` 的 Checklist 第 3 步使用。这一步解决「**怎么把架构结构、依赖、运行时流转读出来当证据**」——3 视角图的节点/边、4 维评估的结论，证据全来自这里。
>
> 本 skill **多语言通用**，不内置完整 code-parsing 工具链；代码读取由 agent 用 LSP/rg + 目录/import 启发完成，证据回链 file:line。证据位置最后由 `validate_evidence.py` 做轻量真实性校验（文件存在、行号范围、note 关键字命中）。

## 一、要读出的五类事实

画图与评估需要的证据，归为五类事实，逐类取证（比单语言坏味道诊断多一类「运行时入口」，因为要画运行时/数据流图）：

| 事实类 | 喂给哪些图/维度 | 怎么读 |
|--------|----------------|--------|
| **模块/层/服务结构** | 分层图、C4、分层&依赖维度、职责内聚维度 | 包/模块声明 + 目录约定 + 服务边界 |
| **依赖边** | 分层图、C4、分层&依赖维度、可扩展性维度 | import / require / `#include` / 全限定引用 / 模块调用 |
| **职责规模** | C4 Component、职责内聚维度、可读性维度 | 类/模块定义 + 方法/字段清单 + 行数（线索） |
| **可见性/暴露面** | C4、职责内聚维度、可读性维度 | 可见性修饰符 / 导出声明（export/public/`__all__`） |
| **运行时入口与流转** | 运行时/数据流图 | 入口（main/router/handler/controller）+ 调用链 + 数据流向 |

## 二、多语言依赖识别：目录/import 启发（主轨）

多语言场景下，依赖边的识别以**目录约定 + import/require 语句**启发为主，LSP 为精度增强（见 §三）。

| 语言 | 模块单元 | 依赖边来源 | 精度 |
|------|----------|-----------|------|
| **JVM(Java/Kotlin)** | package / 类 | `import` + 全限定类型引用（字段/参数/继承/调用） | high |
| **Go** | package / module | `import` + 限定调用（`pkg.Foo`） | high |
| **TypeScript** | module / namespace | `import`/`export` + 类型引用 | high |
| **Python** | package / module | `import` / `from x import y`（动态 import 标 unconfirmed） | medium |
| **C++** | namespace / 目录 | `#include` + 命名空间（宏/前向声明/PIMPL 易漏，标 unconfirmed） | low |
| **JS(纯)/前端框架** | module / 组件 | `import`/`require`/动态 import（动态加载标 unconfirmed） | medium |

- **层识别**：按包/目录约定（controller/service/dao/domain、handler/usecase/repository、components/pages/store/api…）；以**社区惯例命名 + 保守判断**为准（本 skill 不接受规约喂入）。
- **服务边界（app 档位）**：识别服务入口 + 各服务的对外客户端/SDK 调用 + DB/MQ 连接配置，划出服务边界与外部依赖。
- **隐式依赖**（反射、字符串配置、动态加载、IoC 容器注入）——文本级难实锤，标 `unconfirmed: true` 并登记缺口，不硬画成实线边。

## 三、LSP / rg 双轨（精度增强，严格按序）

目录/import 启发是主轨；当需要精确的引用/调用关系（如画运行时流转、确认某类是否被多处依赖）时优先 LSP，没有则降级 rg。

1. **先检测**：对一个代表性源文件做廉价 LSP 探测（如 `documentSymbol` on 一个核心类/模块文件）。
   - 返回结果 → **LSP 可用**，走 §四。
   - 报错（无 language server / 未就绪） → **不可用**，走第 3 步。
2. **可用时用足**（§四）：对核心模块、关键依赖边、运行时调用链用 `incomingCalls`/`outgoingCalls`/`findReferences`/`goToImplementation` 取证。
3. **不可用时默认降级**：不主动安装，不停下来等用户。用第 4 步 `rg` 降级继续，并在 report「评估方法与已知缺口」标注「LSP unavailable，引用覆盖为文本搜索降级」。
4. **用户要求高精度时才等待**：如果用户明确要求必须用 LSP 精确查引用，再给一句安装建议（如「装 pyright/gopls/typescript-language-server/clangd/jdtls 即可用 LSP 精确查引用」）并等待；否则不阻断总览。
5. **降级取证**：无 LSP 时用 `rg` 搜全限定名 / `import` / `#include` / 调用点；疑似关系但无法实锤的标 `unconfirmed: true` 并登记缺口。

> 原则：目录/import 启发先行保证多语言可用；LSP 是精度增强，能用就用、不能用自动降级并留痕。装不装语言服务器是用户的环境决策，不让默认总览卡在工具安装上。

## 四、LSP 可用时的取证清单

| # | 目标 | LSP 操作 | 拿到什么 |
|---|------|----------|----------|
| 1 | 核心模块/类 | `incomingCalls` + `outgoingCalls` | 入度/出度（依赖中枢、职责内聚判断） |
| 2 | 跨模块引用 | `findReferences` | 谁依赖它（分层/依赖方向、循环、跨层边） |
| 3 | 接口/抽象 | `goToImplementation` | 几个实现、主链路走哪个（可扩展性判断） |
| 4 | 运行时调用链 | `outgoingCalls` 从入口递归 | 请求流转路径（运行时/数据流图） |
| 5 | 字段/可见性 | `documentSymbol` | 导出/暴露面（职责边界、可读性） |

无 LSP 时逐行换成「rg 搜符号名 → 人工判调用/引用关系」，节首标注降级。

## 五、运行时入口与流转识别（运行时/数据流图专用）

画运行时/数据流图需要识别「一次典型请求/操作怎么在架构里流动」：

1. **找入口**：按语言/框架找——Web 路由（`@GetMapping`/`app.route`/`router.get`/`@Controller`）、消息消费者、定时任务、CLI 命令、事件 handler。
2. **追主链路**：从入口沿调用链追 2-5 跳（入口 → service/usecase → domain/repository → 外部依赖），记录每一步的 file:line。
3. **标数据流向**：请求进、响应出、DB 读写、外部调用、消息发布/消费的方向。
4. **入口缺失**（纯库模块无运行时入口）→ 运行时视角标「不适用/信息不足」+ 原因（见 `architecture-diagrams.md` 视角适用性）。

## 六、大范围聚焦策略（PRD §6 噪音/聚焦，app 级尤其关键）

app 级或大模块范围偏大，全量精读会 token 爆炸 + 噪音淹没关键结构。**热点优先 + 分层聚合**：

1. **先聚合后精读**：先按模块/服务/目录聚合（粗粒度），把 N 千个文件收敛成几十个模块/服务节点，再决定哪些下沉到类级精读。
2. **热点优先**：被很多模块依赖的模块（高入度）、依赖很多外部（高出度）、体积异常大的模块——这些是结构关键点，优先取证。
3. **分层扫描**：先读模块/层/服务结构（粗），锁定可疑层/边界，再下沉到类/方法（细）。
4. **抽样确认**：非热点模块抽样确认「无重大结构异常」即可，不逐行精读，抽样在「已知缺口」说明。
5. **不淹没**：图与评估只报**真实结构事实**，不罗列每个文件的细枝末节。

> 聚焦策略的产出是「在有限 token 内抓到架构骨架与关键设计」。在 report「评估方法/已知缺口」节简述本次用了哪种聚焦 + 舍弃了什么（防「看似全覆盖实则抽样」的误导）。

## 七、防臆造（底线）

- 每条证据回链真实 `file:line`；rg/LSP 命中**只当线索**，是否真构成结构事实要看代码确认（注释/命名可能过时，以代码为准）。
- 推断但没实锤的（隐式依赖、动态加载、跨语言边界）标 `unconfirmed: true` 并登记「已知缺口」，不混进图当实线边、不混进评估当事实。
- **禁止编造证据**：找不到定位点的结论必须标「未能定位」，不得编 file:line；找不到的图节点必须标 `⚠ 未确认`，不得编造节点或边。
