# 4 维正向评估 + 业界做法对照（模块 C 主轴）

> 配合 `arch-overview` 的 Checklist 第 5 步使用。本文件是「**整体设计好不好**」的评估骨架：4 个维度逐维**正向评估现状**，每维**对照业界成熟做法**立标杆，指出现状与标杆的差距。这是正向总评，**不是坏味道逐条诊断**（那是 `arch-quality-eval`）。
>
> **业界做法来源纪律**：所有业界做法均为 **LLM 内置经验**（训练知识），**不联网、不假装权威**。每条声明 `provenance: "LLM内置经验"` + `verified: false`（未核对原文）+ 至少一个 `further_reading` 延伸方向（经典资料名 / 模式名 / 可检索关键词），供用户自行核实。对齐 `outputs-declare-knowledge-source` 原则。

## 一、怎么用这个 rubric

1. **4 维全评**：每个维度都必须有结论（全覆盖，不漏维度）。每维结论 = 现状评价 + 业界做法对照 + 证据。
2. **正向表述**：评「这个维度设计如何」，给档位（优/良/中/差，判定见 `scoring-and-grading.md`），不是找坏味道逐条列。
3. **业界对照立标杆**：每维挑 1-3 条最相关的业界成熟做法作对照，指现状与标杆的差距方向（不是逐条罗列所有做法）。
4. **证据驱动**：现状评价挂证据（回链 3 视角图节点/边 + 代码 file:line）；找不到的标 `⚠ 未确认`，**禁止编造**。
5. **不越界**：这里**不分级 critical/major/minor、不下 go/no-go、不给重构方案**（那是 `arch-quality-eval`）。前瞻性风险点在 `scoring-and-grading.md` 里以「风险点」形式给。

## 二、4 维度概览

| key | 维度 | 评什么 | 主要证据来源 |
|-----|------|--------|-------------|
| `layering` | 分层 & 依赖方向 | 层次划分是否清晰、依赖方向是否合理（有无反向/跨层/循环） | 视角①分层/模块依赖图 + 依赖边 |
| `cohesion` | 职责内聚 & 边界 | 模块/组件是否单一职责、边界清晰、高内聚低耦合 | 视角②C4 组成 + 职责规模/可见性 |
| `extensibility` | 可扩展性 & 可变性 | 新增能力是否容易、变化点是否被隔离、有无过度设计 | 视角③运行时流转 + 接口/扩展点 |
| `readability` | 可读性 & 命名表意 | 结构能否一眼看懂职责、命名是否表意、约定是否一致 | 3 视角共同 + 命名/结构 |

> 维度顺序固定为 `layering → cohesion → extensibility → readability`，写入 `overview.json` `dimensions[]`，`validate_overview.py` 按此校验齐全。

## 三、维度 1：分层 & 依赖方向（layering）

**评什么**：代码是否按层/职责组织？依赖是否单向、指向稳定方向？有没有反向、跨层、循环依赖让结构难以理解与演进？

**现状评估关注点**：
- 层划分是否清晰、层职责是否单一（Web/应用/领域/基础设施各司其职）。
- 依赖方向是否单向（上层→下层）；有无反向（下层依赖上层）、跨层（Web 直连 DAO）、循环（A↔B）。
- 跨服务/跨模块依赖是否合理、是否指向更稳定方。

**业界成熟做法对照库**（挑相关条目对照，全部 provenance=LLM内置经验 / verified=false）：

| 做法 | 是什么 | 适用前提 | 经典出处（延伸阅读方向） |
|------|--------|----------|------------------------|
| **分层架构 Layered Architecture** | 按职责分层（表现/领域/数据），上层依赖下层，不跨层不反向 | 职责可清晰分层的企业应用 | Layered Architecture（经验模式）；《领域驱动设计》分层 |
| **依赖倒置 DIP** | 高层不依赖低层细节，都依赖抽象（接口）；细节依赖抽象 | 高层需隔离低层变化时 | SOLID·DIP；Robert Martin |
| **洁净架构 Clean Architecture** | 依赖指向内（外层依赖内层 domain 核心），核心业务不依赖框架/外部细节 | 想让业务核心独立于框架/DB/外部 | 《Clean Architecture》Robert Martin |
| **六边形架构 Hexagonal / 端口适配器** | 业务核心定义端口，外部交互作为适配器接入；核心不依赖外部细节 | 需要多个外部交互渠道/可替换适配器 | Hexagonal Architecture（Alistair Cockburn） |
| **稳定依赖原则 SDP** | 依赖应指向更稳定（更难变）的方向 | 模块稳定性差异明显时 | 《敏捷软件开发》SDP（Robert Martin） |

> 对照写法示例：「现状：`Controller` 直接依赖 `Repository`（视角①边 `OrderController.java:33`），跨过 Service 层。业界做法（分层架构）要求上层经服务层访问数据层，不跨层。差距：存在跨层依赖，分层不纯净。——provenance: LLM内置经验，未核对；延伸阅读：Layered Architecture。」

## 四、维度 2：职责内聚 & 边界（cohesion）

**评什么**：模块/组件是否单一职责？边界是否清晰（该在一起的在一起、该分开的分开）？是高内聚低耦合，还是职责混杂、边界模糊？

**现状评估关注点**：
- 模块/类是否单一职责（一个变化理由）；有无承担过多职责的「上帝类/包」。
- 边界是否清晰：该内聚的（同一业务能力的）是否在一起；该隔离的（不同业务能力的）是否分开。
- 耦合是否过紧：模块间是否大量直接依赖细节而非抽象；信息隐藏是否到位。

**业界成熟做法对照库**：

| 做法 | 是什么 | 适用前提 | 经典出处（延伸阅读方向） |
|------|--------|----------|------------------------|
| **单一职责 SRP** | 一个模块/类只有一个变化的理由（一个职责） | 通用 | SOLID·SRP（Robert Martin） |
| **高内聚低耦合** | 模块内元素强相关（内聚），模块间依赖最小（耦合） | 通用 | 经典设计原理 |
| **限界上下文 Bounded Context（DDD）** | 按业务能力划分模型边界，每个上下文内模型一致、上下文间明确翻译 | 复杂业务领域 | 《领域驱动设计》Eric Evans；DDD Strategic Design |
| **信息隐藏 / 封装** | 只暴露必要接口，内部实现封闭 | 通用 | Parnas 信息隐藏；《面向对象设计》 |
| **接口隔离 ISP** | 不强迫依赖方依赖它用不到的接口；接口按消费方细分 | 接口臃肿时 | SOLID·ISP |

## 五、维度 3：可扩展性 & 可变性（extensibility）

**评什么**：新增能力容易吗？变化点（频繁变动的部分）是否被隔离？是恰到好处的扩展点，还是过度设计（为想象的需求过度抽象）/ 变化散落（一个改动要动多处）？

**现状评估关注点**：
- 扩展是否开放：新增一类能力（如一种支付方式、一种通知渠道）是否只需新增而非大改既有代码（OCP）。
- 变化点隔离：易变部分（规则、策略、配置）是否被抽象/配置化，与稳定核心分离。
- 过度设计 vs 不足：有无为未发生的 needs 过度抽象（YAGNI 违背），或该抽象却硬编码。
- 变更散落：一类改动是否散落到多处（视角③链路里多个无关组件）。

**业界成熟做法对照库**：

| 做法 | 是什么 | 适用前提 | 经典出处（延伸阅读方向） |
|------|--------|----------|------------------------|
| **开闭原则 OCP** | 对扩展开放、对修改关闭：新增行为靠扩展（多态/策略），不改既有代码 | 变化方向明确时 | SOLID·OCP（Robert Martin） |
| **策略模式 Strategy / 多态扩展** | 把易变的算法/行为抽成可替换策略，运行时选择 | 同一操作有多种实现 | GoF Strategy；多态 |
| **配置/插件驱动** | 把变化点外置为配置或插件，核心逻辑不变 | 变化频繁且可枚举 | Twelve-Factor App（配置分离）；插件架构 |
| **依赖注入 DI** | 通过注入抽象解耦具体实现，便于替换与扩展 | 需要解耦与可替换时 | DI 模式；Martin Fowler |
| **YAGNI / 避免过度设计** | 不为当前不需要的需求做抽象；演进式添加 | 通用，警惕过度设计 | XP·YAGNI；演进式架构 |
| **演进式架构 Fitness Function** | 用可自动验证的"适应度函数"保护架构重要特征演进 | 长期演进系统 | 《演进式架构》Ford/Parsons |

> 注意：可扩展性维度要**同时看两面**——扩展性不足（变化散落/硬编码）和过度设计（为想象需求过度抽象）都是减分项。

## 六、维度 4：可读性 & 命名表意（readability）

**评什么**：结构能否让人一眼看懂职责与依赖？命名是否表意（语义层）？约定是否一致？——只评**架构层**可读性，**不含 lint 能查的代码风格**（缩进/命名格式/import 顺序）。

**现状评估关注点**：
- 结构自解释：看模块/层/服务的结构与命名，能否快速建立心智模型。
- 命名表意（语义层）：包/类/模块名是否反映其职责；有无 `Manager`/`Helper`/`Util`/`XxxServiceImpl` 这类不表意的万能名；名字与职责是否矛盾。
- 约定一致性：同类事物是否用一致的命名/组织约定（约定优于配置）。
- 依赖可理解：有无「为什么它会依赖这个」的费解边。

**业界成熟做法对照库**：

| 做法 | 是什么 | 适用前提 | 经典出处（延伸阅读方向） |
|------|--------|----------|------------------------|
| **语义命名 Semantic Naming** | 名字反映职责与意图，避免万能/无信息名 | 通用 | 《代码整洁之道》命名（Robert Martin） |
| **约定优于配置 Convention over Configuration** | 用一致的约定减少认知负担，例外才显式配置 | 框架/团队规范 | Rails CoC；Spring 约定 |
| **关注点分离 SoC** | 不同关注点分到不同模块，结构上可辨 | 通用 | SoC（Dijkstra）；信息隐藏 |
| **领域语言 Ubiquitous Language** | 代码命名用业务领域统一语言，消除业务-代码翻译 | DDD 场景 | 《领域驱动设计》Ubiquitous Language |

> 划界：本维度只取「命名是否**表意**」「结构是否**自解释**」（语义/结构层）；「命名是否符合驼峰规范」「import 顺序」「缩进」属 lint，**不评**。

## 七、业界做法对照的 provenance 纪律（强制）

每条用于对照的业界做法，在 `overview.json` `dimensions[].industry_practice` 必须含：

| 字段 | 要求 |
|------|------|
| `what` | 该做法是什么（一句话） |
| `when` | 适用前提/场景 |
| `gap` | 现状与标杆的差距方向（具体到证据） |
| `provenance` | 固定字符串 `"LLM内置经验"`（不写「权威」「业界共识」等暗示已核实的措辞） |
| `verified` | 固定 `false`（未核对原文） |
| `further_reading` | 字符串数组，≥1 个可检索的延伸方向（经典资料名 / 模式名 / 关键词，如 `"《Clean Architecture》Robert Martin"`、`"Hexagonal Architecture"`） |

> 正文中业界做法措辞纪律：用「业界常见做法是…」「经典模式如…」**这种经验性措辞**；**禁止**用「最佳实践证明…」「权威资料表明…」这种暗示已联网核实的措辞。`validate_report.py` 会检查每维度的业界对照段是否含 provenance/未核对声明。

## 八、与 3 视角图、与 arch-quality-eval 的衔接

- **证据来自图**：每维度的现状评价应回链 3 视角图的节点/边（视角①→layering，视角②→cohesion，视角③→extensibility，三视角→readability），图是评估的视觉证据。
- **不越界成坏味道诊断**：评估只说「这个维度设计如何 + 与业界标杆的差距」；若发现具体的循环依赖/God Class 等**结构性问题**，只作为「该维度现状」的事实呈现 + 可在「风险点」前瞻性点出，**不在这里分级 critical/major/minor、不下 go/no-go、不给重构方案**——那是 `arch-quality-eval` 的职责。

## 九、自检

1. **4 维全评** —— 4 个维度都有结论，无漏维。
2. **正向表述** —— 评「设计如何」，不是逐条列坏味道。
3. **业界对照齐全** —— 每维有至少 1 条业界做法对照（what/when/gap），且有 provenance=LLM内置经验 + verified=false + ≥1 延伸阅读。
4. **措辞不假装权威** —— 用经验性措辞，无「最佳实践证明」「权威表明」。
5. **证据回链** —— 现状评价挂 file:line / 图节点；无编造。
6. **没混 lint** —— readability 维度只评语义/结构层，无格式/import 顺序评判。
7. **没越界** —— 无 critical/major/minor 分级、无 go/no-go、无重构方案（留给 arch-quality-eval）。
