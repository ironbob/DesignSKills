# 范围界定与边界（模块 A）

> 配合 `arch-overview` 的 Checklist 第 1、2 步使用。这一步圈定「**画哪一块、评哪一块**」——边界定错，后面全错。**范围未经用户确认前不画图、不评估、不产出**（HARD-GATE）。

## 一、模块 A 三件事（PRD §4-A）

1. **范围档位指定**（P0）：接受用户指定本次是**模块级**还是 **app/服务级**，及对应根路径（可跨多目录）。
2. **多语言技术栈识别 + 精度标注**（P0）：识别范围内的主要语言（Python / Go / JS / TS / 前端 / JVM / C++ 等），及其包/目录/模块组织结构；**逐语言标注结构/依赖分析精度**。
3. **覆盖范围枚举**（P0）：枚举本次覆盖的文件/目录/包/外部依赖集合。

> 注意：本 skill **不做项目规约喂入**（不做规约违规检测，那是 `arch-quality-eval` 的）。范围界定只问「画哪、什么栈」，不问「对照什么规约」。

## 二、范围档位：module vs app（最关键的第一问）

先问用户本次要总览的范围档位，它决定图的粒度与 token 规模：

| 档位 | 含义 | 图的粒度 | 典型输入 |
|------|------|----------|----------|
| **module** | 一个模块 / 子系统 / 包集合 | 模块内部的包/层/类依赖与职责 | `src/order/`、`packages/auth/`、`com.x.order.*` |
| **app** | 一个完整 app / 服务，含其内部模块边界 + 外部依赖（DB/第三方/其他服务） | 服务/容器/组件组成 + 跨模块依赖 + 外部边界 | 一个服务仓库根、一个 monorepo 子 app |

- **用户必须明确选档位**；若只给路径不说档位，主动问一句「这是要总览一个模块，还是整个 app/服务？」
- **app 档位** 会引入外部依赖节点（DB / MQ / 第三方 API / 其他服务）——这是 app 级总览的价值，也是 `arch-quality-eval` 明确不做的事。

## 三、怎么圈范围

### 3.1 输入形态
- 用户给一个或多个**根路径/目录/包**（如 `src/` + `internal/`）。
- 可能给一个**目标名**（如「订单服务」「支付模块」）+ 路径；路径是主，名是标签。
- **app 档位**：根路径通常是服务仓库根或 monorepo 的 app 子目录。

### 3.2 圈出覆盖文件集合（`covered_files`）
- 用 `rg --files` / `find` 枚举路径下源文件，按语言后缀过滤（`.py`/`.go`/`.ts`/`.tsx`/`.js`/`.jsx`/`.vue`/`.java`/`.kt`/`.cpp`/`.h`…），剔除 build/dist/node_modules/.git/测试/resource 产物（除非用户明确含）。
- **跨多目录**：把用户给的多个根合并成一个覆盖集合。
- 结果写进 `overview.json` 的 `covered_files`（**非空**，显式声明优于推断——防「声称画了其实没看」）。
- 文件过多（app 级常见）时：用 `analysis-protocol.md §六` 的聚焦策略，但在 `covered_files` 里**声明覆盖集合**（即便精读的是热点子集，覆盖边界仍是全集，抽样部分在「已知缺口」说明）。

### 3.3 多语言技术栈识别
- 按文件后缀 + 内容判定主要语言；**以代码量/文件数占比显著的语言为主**，其余为辅。
- 混合栈（如前后端同仓库、TS + Python）——**全部列出**到 `languages`，不合并成单一语言。
- 逐语言标注精度（见 §四）。

### 3.4 结构识别（粗读，不深挖）
- 读各语言的包/模块声明 + 目录约定，识别模块/层结构与服务边界（controller/service/dao/domain、handler/usecase、components/…）。
- **app 档位**额外识别：服务入口（main / index / app bootstrap）、外部依赖配置（DB 连接、第三方 SDK、其他服务客户端）。
- 这一步只够划边界 + 定热点，**深挖在第 3 步**（确认范围后）。

## 四、各语言精度标注（PRD §6，必须诚实）

不同语言的结构/依赖分析精度差异大，必须在范围确认时告诉用户、并写进 `language_precision`：

| 精度 | 典型语言 | 原因 |
|------|----------|------|
| **high** | JVM(Java/Kotlin)、Go、TypeScript | 有规范的包/模块系统 + 显式 import，依赖边可靠 |
| **medium** | Python、C#、Swift | import 相对规范但动态特性/反射可能藏隐式依赖 |
| **low** | C++、JavaScript(纯 JS)、动态加载为主的语言 | 依赖靠 `#include`/目录约定/动态 require，文本级易漏隐式边 |

- `language_precision` 每项 `{language, precision, note}`；**low/medium 的语言在报告里结论更保守、登记缺口**。
- **不照搬单语言精度下结论**：一个 high 语言 + 一个 low 语言混编的 app，low 那部分的图与评估要单独标注精度受限。

## 五、两段式确认（HARD-GATE，第 2 步）

把下面六样呈现给用户确认，**未确认不进第 3 步**：

1. **范围档位**（module / app）+ **根路径**。
2. **覆盖文件集合**（`covered_files` 概要：N 个文件 / 涉及哪些目录或包；app 档位列出识别到的服务/模块边界 + 外部依赖）。
3. **多语言技术栈**（`languages` 清单 + 各语言占比）。
4. **各语言精度**（`language_precision`：哪些 high / medium / low）。
5. **一句话架构职责**（这个模块/app 是干什么的，作为评估基线；不是「应有架构」，只是「它声称做什么」）。
6. （可选）**视角适用性初判**（如纯库模块可能无运行时入口，预告第 3 视角或受限）。

> 最大风险是「圈错范围 / 把无关代码拉进来或漏掉关键模块 / 漏掉 app 级的外部依赖」。这一步专门拦它。用户修订后回到本步重确认。

## 六、边界越界识别（scope 判定）

- **用户要「全 repo 批量巡检 / 多 app 矩阵」** → 超出本 skill（PRD §5）；建议收窄到一个模块或一个 app。
- **app 档位范围过大**（整个巨石 monorepo 含十几个服务）→ 提示「app 级总览在超大范围上 token/噪音压力大，建议聚焦到单个服务或一组紧密服务」，用聚焦策略（§3.2 / `analysis-protocol.md §六`）。
- **范围过小到单文件** → 可总览，但提示「单文件级架构意义有限，图与评估价值低，建议至少到模块/子系统级」。
- **用户要画部署图** → 超出范围（PRD §5 不做部署视图），明确说本 skill 不画部署/运维拓扑。

## 七、划界：不做什么（PRD §5）

- ❌ 不做全 repo 批量巡检 / 多 app 全景矩阵。
- ❌ 不做项目规约喂入 / 规约违规检测（那是 `arch-quality-eval`）。
- ❌ 不自动解析项目架构文档（ARCHITECTURE.md 等）。
- ❌ 不从代码结构推断「应有架构」当标准——只呈现现状 + 对照业界成熟做法。
- ❌ 不画部署 / 运维拓扑视图。
